# Authentication and authorization (as built)

Design source: `docs/adr/0002-roles-as-application-claims.md` (why roles are app-managed, not baked into the identity provider's own claims), `docs/design/low-level-design.md` "Authorization model". Authentication itself was originally Microsoft Entra External ID (`docs/adr/0001-technology-stack.md`) — **STATE.md's "Identity" item replaced that with self-rolled ASP.NET Core Identity (built-in TOTP MFA)** as part of the hosting pivot to a self-hosted VPS (`docs/adr/0005-hosting-pivot-self-hosted-vps-postgresql.md`), and replaced the Microsoft Graph guardian-invitation mechanism with a self-rolled signed/single-use/expiring invite link (see [guardian-links.md](guardian-links.md)). This page describes the Identity-era design; the Entra-era history (the interactive-render-mode checker round-trip in particular) is kept below because the *property* it proves still matters and the new code was deliberately built to preserve it, not because Entra is still in the codebase.

## `AppUser`/`UserRole` vs ASP.NET Core Identity: the coexistence design

This is the load-bearing judgement call of the whole item, recorded in full on `AppUser`'s own doc comment (`src/Vlms.Domain/AppUser.cs`) — read it before touching either type.

- **`AppUser` (`Vlms.Domain`) stays a plain POCO.** It does not inherit `IdentityUser<int>`. `adr/0002-roles-as-application-claims.md`'s decision — roles are the app-owned `UserRole` table, never baked into the identity provider's own claims/role store — is explicitly unaffected by the Entra→Identity swap; `AppUser` is still the thing every other entity's FK points at (`Student.AssignedTeacherUserId`, `ParentGuardian.AppUserId`, `LessonChangeProposal.ProposedByUserId`, ...).
- **`VlmsIdentityUser : IdentityUser<int>` (`Vlms.Infrastructure/Identity/VlmsIdentityUser.cs`) is a separate type**, holding Identity's own credential/store row (password hash, security stamp, TOTP secret, `TwoFactorEnabled`, lockout fields). Keeping it in Infrastructure, not Domain, matches this codebase's existing Domain-interface/Infrastructure-implementation split (`ICurrentUserContext`/`IBlobStorage`/`INotificationService`) — Domain stays free of any ASP.NET Core package dependency.
- **The two rows share a primary key** — the same `int` value, not an independent surrogate key with its own FK column — because every existing FK in this schema already treats `AppUser.Id` as *the* stable user identifier; a separate surrogate key on the Identity side would just be a second number to keep straight for no benefit. `VlmsIdentityUser.Id` is the one place in this schema left at EF Core's default `ValueGeneratedOnAdd` (Identity's `UserManager.CreateAsync` inserts it and lets the database assign the id); `AppUser.Id` stays `ValueGeneratedNever`, but its value is always copied from the just-created `VlmsIdentityUser.Id`, never computed independently (unlike the old Entra-era `UserProvisioningService`'s `Max(Id)+1`).
- **This pairing is enforced in exactly one place**: `Identity/AppUserProvisioningService.cs`'s `CreateAsync` — `UserManager<VlmsIdentityUser>.CreateAsync` followed by inserting the paired `AppUser` row, both against the same DI-scoped `VlmsDbContext`, composing with an ambient transaction if the caller already opened one (see its own doc comment for the "detect `Database.CurrentTransaction`" pattern) rather than always opening its own. It is **not** enforced as a real database foreign key — tried, then reverted, because it would have forced every one of this codebase's ~150 pre-existing tests that seed a bare `AppUser` row (to represent "a user holding this role") to also fabricate a matching `VlmsIdentityUser` row for a constraint unrelated to what those tests are about. `AppUserProvisioningService` is the only code path anywhere that creates an `AppUser` row, so an orphan can only occur via a bug in that one class — guarded by `AppUserProvisioningServiceTests`.

## Sign-in wiring (`src/Vlms.Web/Program.cs`)

`AddIdentityCore<VlmsIdentityUser>()` (not `AddIdentity`) + `.AddSignInManager()` + `.AddDefaultTokenProviders()` + `.AddEntityFrameworkStores<VlmsDbContext>()` — the leaner "no role store" combination, since ASP.NET Core Identity's own role feature (`AspNetRoles`/`AspNetUserRoles`) is never used (roles stay `UserRole`, per adr/0002, unaffected by this swap). `VlmsDbContext` itself inherits `IdentityUserContext<VlmsIdentityUser, int>` (not `IdentityDbContext`, which would add the role tables this codebase doesn't want) and calls `base.OnModelCreating` first, reusing Microsoft's own tested configuration for Identity's four store tables. `AddAuthentication` sets `IdentityConstants.ApplicationScheme`/`.ExternalScheme` via `.AddIdentityCookies()` — the standard Identity cookie wiring, verified against `learn.microsoft.com/aspnet/core/blazor/security/server` rather than assumed.

`options.SignIn.RequireConfirmedAccount = false` — still the case even though SMTP now exists (`Vlms.Domain.IEmailSender`/`SmtpEmailSender`, STATE.md's "Email" hosting-pivot item, wired for `NotificationService`/`GuardianInviteService`): nothing wires ASP.NET Core Identity's own confirmation-email mechanism (a distinct `Microsoft.AspNetCore.Identity.UI.Services.IEmailSender` contract Identity's account-confirmation flow depends on, not this project's `IEmailSender`), so requiring confirmation would still permanently lock out every new account.

## Provisioning: `AppUserProvisioningService` (`src/Vlms.Infrastructure/Identity/AppUserProvisioningService.cs`)

Creates the paired `VlmsIdentityUser`/`AppUser` row (see the coexistence section above). Used by two callers: the general `/Account/Register` self-service page, and the guardian invite-accept flow (`GuardianInviteService.AcceptAsync` — see [guardian-links.md](guardian-links.md)). **A newly created `AppUser` still gets zero `UserRole` rows** — deny-by-default, the one property STATE.md's item explicitly required to survive the swap. Role assignment is a separate, Admin-only action — see "Role assignment and first-Admin bootstrap" below.

**This retires the Entra-era `Provisioning/UserProvisioningService.cs`, and is not a rename of it** — that service's whole reason to exist was *find*-or-create against a federated OIDC claim on every successful Entra sign-in (`OnTokenValidated`), where the account itself was created by Entra's hosted sign-up flow and this codebase only learned about it after the fact. Local Identity has no equivalent federated-provisioning moment — every account is created by an explicit action this codebase's own code drives end to end — so there is nothing left to "find", only "create". Repurposing the old find-or-create shape onto a create-only flow would have left a dead "find" branch pretending to be a rename; a fresh class was written instead.

## `ICurrentUserContext` implementations

- `NullCurrentUserContext` — deny-by-default, for design-time/migrations tooling and as an internal lookup-context (see [access-control.md](access-control.md)). `HasMfaEnabled` is `false`. Never wire as the runtime context.
- `SystemCurrentUserContext` — for the `Vlms.Jobs` WebJob host, no signed-in human caller. Grants exactly `Role.Admin`/`Role.SafeguardingOfficer`; `HasMfaEnabled` is hardcoded `true` (documented reasoning: MFA enforcement gates *interactive sign-in by a human*, which this trusted, narrowly-scoped system principal is not — the same reasoning that already narrowly scopes its roles).
- `IdentityCurrentUserContext` (`src/Vlms.Infrastructure/Security/IdentityCurrentUserContext.cs`) — the real one, replacing the Entra-era `EntraCurrentUserContext`. Resolves `UserId`/`Roles`/`HasMfaEnabled` from a short-lived `VlmsDbContext` of its own (never the DI-resolved instance — it is itself a constructor dependency *of* `VlmsDbContext`, so depending on the DI-resolved one would be circular), keyed by the caller's `ClaimTypes.NameIdentifier` claim — which under Identity *is* the shared `AppUser`/`VlmsIdentityUser` id directly, no lookup join needed (unlike the Entra object-id claim it replaces). Two constructors, same shape as the Entra-era class: one takes an already-resolved `ClaimsPrincipal` (tests, no ASP.NET Core hosting needed); the other takes the `AuthenticationStateProvider` itself and is what `Program.cs` uses at runtime, deferring resolution until `UserId`/`HasRole`/`HasMfaEnabled` is actually read (see the next section for why this still matters under Identity). **Re-read on every call, never cached (FR-016, 22/10/2026):** each read re-resolves the principal and runs one primary-key query, so a role granted or removed, or 2FA disabled, takes effect on the user's next action, including in interactive pages already open. It used to resolve once through a `Lazy` and keep the result for the DI scope, which in a Blazor Server circuit is the circuit's whole lifetime. See [Role changes and multiple roles](#role-changes-and-multiple-roles-fr-016) below.

## Resolving the caller's `ClaimsPrincipal`: `AuthenticationStateProvider`, not `IHttpContextAccessor`

`Program.cs` builds `IdentityCurrentUserContext` from the `AuthenticationStateProvider` itself, which internally resolves the `ClaimsPrincipal` via `AuthenticationStatePrincipalResolver.Resolve(AuthenticationStateProvider)` (`src/Vlms.Infrastructure/Security/AuthenticationStatePrincipalResolver.cs`), not `IHttpContextAccessor.HttpContext?.User`. This closes a gap the codebase originally shipped with under Entra (flagged by a checker review on commit c318bc5, generalized here since the underlying framework behaviour is Blazor Server's own circuit lifecycle, not Entra-specific): `IHttpContextAccessor.HttpContext` is null outside the request that established a Blazor Server interactive (SignalR circuit) render — so the old code resolved to an empty principal (fails closed, safe, but denies every authorised user) the moment a page went interactive. `AuthenticationStateProvider` doesn't have this limitation: ASP.NET Core's built-in Blazor Web App wiring (`builder.Services.AddCascadingAuthenticationState()`, in `Program.cs`) captures `HttpContext.User` once — during static SSR/the request that establishes the circuit — and flows it through the rest of the circuit's lifetime, including every subsequent interactive render.

Under Identity, `Program.cs` registers `IdentityRevalidatingAuthenticationStateProvider` as the concrete `AuthenticationStateProvider` — the officially documented provider for Blazor Web App + Server interactivity + ASP.NET Core Identity (`learn.microsoft.com/aspnet/core/blazor/security/server`), which periodically re-validates the caller's security stamp so a revoked/changed credential doesn't stay "signed in" indefinitely for a connected circuit. **Verified, not assumed, that the safety argument below still holds under this provider**: `IdentityRevalidatingAuthenticationStateProvider` subclasses `RevalidatingServerAuthenticationStateProvider`, itself a subclass of the same `ServerAuthenticationStateProvider` the Entra-era provider used — `GetAuthenticationStateAsync()` is unchanged by revalidation; the periodic re-validation runs on its own background timer, not inside that call.

`AuthenticationStatePrincipalResolver.Resolve` blocks synchronously (`GetAwaiter().GetResult()`) on `GetAuthenticationStateAsync()` rather than awaiting it, because `ICurrentUserContext.HasRole`/`UserId`/`HasMfaEnabled` must stay synchronous (they run inside `VlmsDbContext`'s EF Core query filter lambdas — adr/0004-sensitive-data-access-control.md — which can't be made async). **This is safe only for consumers that resolve `ICurrentUserContext` inside a rendered Razor component's DI scope** (interactive pages/policies, resource-based authorization handlers) — by that point the framework has already captured and stored the `AuthenticationState`, so `GetAuthenticationStateAsync()` returns an already-completed `Task`: no blocking on live I/O, no deadlock. It is **not** safe in general: a checker round-trip under Entra (STATE.md's log, follow-up on commit d2adf82) found that this codebase originally called `AuthenticationStatePrincipalResolver.Resolve` *eagerly*, inside `Program.cs`'s `ICurrentUserContext` DI factory, before constructing the current-user-context implementation. That factory also runs during account-creation/sign-in flows (`AppUserProvisioningService`/`GuardianInviteService.AcceptAsync` → `VlmsDbContext` → `ICurrentUserContext`, under Identity; `UserProvisioningService`'s OIDC callback under Entra), which is not a rendered component's DI scope — `ServerAuthenticationStateProvider` throws `InvalidOperationException` there because no component has called `SetAuthenticationState` yet.

**The actual fix, and the property that now holds — carried over unchanged into the Identity-era class:** resolution is genuinely deferred, not merely moved. `IdentityCurrentUserContext`'s `AuthenticationStateProvider` constructor stores the provider and only calls `AuthenticationStatePrincipalResolver.Resolve` when `UserId`/`HasRole`/`HasMfaEnabled` is read (since FR-016, on every such read rather than once through a `Lazy<...>`). `Program.cs`'s DI factory doesn't call `Resolve` itself — it just passes the `AuthenticationStateProvider` through. Neither `AppUserProvisioningService` nor `GuardianInviteService.AcceptAsync` reads `ICurrentUserContext.UserId`/`HasRole`/`HasMfaEnabled` on the newly-created account's context (they don't even construct one for it — `AppUser` rows are written directly), so no throw occurs regardless of DI scope. Verified by `AuthenticationStatePrincipalResolverTests` and `IdentityCurrentUserContextTests` (`tests/Vlms.Tests/Infrastructure/`).

Routes.razor uses `AuthorizeRouteView` (not a plain `RouteView`), which is what makes a page's `@attribute [Authorize(Policy = "...")]` actually enforced, cascading the resulting `Task<AuthenticationState>` down to the page — see [web.md](web.md).

## Authorization model

- **Role-based**: one ASP.NET Core policy per `Role` enum value (`RequireAdmin`, `RequireTeacher`, ...), backed by `RoleRequirement`/`RoleAuthorizationHandler`.
- **Resource-based** (`StudentAccess` policy, `StudentAccessRequirement`, resource type `Student`):
  - `ParentStudentAccessHandler` — succeeds only if the target `Student` is reachable via `StudentGuardianLink` from a `ParentGuardian` whose `AppUserId` matches the caller. Delegates the actual join to `ParentGuardianLinkage.IsLinkedAsync` (`src/Vlms.Infrastructure/Authorization/ParentGuardianLinkage.cs`, extracted alongside the parent dashboard — see [parent-dashboard.md](parent-dashboard.md)) — verified per-student, not per-parent-in-general. `ParentGuardianLinkage.LinkedStudentIds` is the same relationship enumerated the other direction, used by `Engagement.ParentDashboardService` to list all of a Parent's own linked students.
  - `StudentSelfAccessHandler` — succeeds only if `resource.AppUserId == callerUserId`. Null-safe both ways: an unlinked student (`AppUserId == null`) and a caller with no resolved `UserId` both correctly fail rather than accidentally matching each other.
  - `TeacherStudentAccessHandler` — role-only (Teachers see all students by design, `docs/design/low-level-design.md`), no per-resource check.

All three were adversarially checked (Opus-model checker) for the specific failure mode of "the deny path is accidentally permissive" — confirmed clean, see `STATE.md`'s log entry for that review.

## Roles per chapter (FR-021, adr/0010)

Chapter roles (Admin, Teacher, Safeguarding Officer, Parent, Student) are `UserRole` rows with a `ChapterId` and count only in the caller's active chapter (`IdentityCurrentUserContext.ActiveChapterId`, from `ChapterMembership`); national roles (Approver, National Administrator) have no chapter. `RoleAssignmentService` works on the Admin's active chapter; `FirstAdminBootstrapService` grants Shrewsbury's Admin and, via `BootstrapNationalAdministratorAsync` (`Vlms.Jobs bootstrap-national-admin`), the first National Administrator. `MfaRequirementHandler` also gates National Administrator. Details: [chapters.md](chapters.md).

## Role changes and multiple roles (FR-016)

- **One identity, any combination of roles; permissions fixed per role.** A user may hold, for example, Teacher+Admin, Teacher+Safeguarding Officer or Teacher+Parent. There is no permission layer beyond the per-role policies, query-filter arms and in-service checks, so a multi-role user gets exactly the union. A student sign-in holds only Student (`RoleAssignmentService` refuses anything else, unchanged).
- **Immediate effect.** `IdentityCurrentUserContext` re-reads roles and MFA on every check (above), so the next authorization check or query-filter evaluation sees the change, even inside a long-lived circuit. The cost is one small query per check; no per-request or per-render cache was added, because a circuit has no request boundary to tie one to.
- **Security stamp.** `RoleAssignmentService.GrantAsync`/`RevokeAsync` (and so `ApproveGuardianAsParentAsync`) and `LeavingService.MarkStaffLeftAsync` call `SecurityStamps.RotateAsync` (`src/Vlms.Infrastructure/Identity/SecurityStamps.cs` → `UserManager.UpdateSecurityStampAsync`) in the same transaction as the change. Self-service 2FA enable/disable/reset already rotates the stamp inside `UserManager`. An Admin who changes their own roles is therefore signed out at the next validation.
- **Validation interval.** `VlmsIdentityPolicy.SecurityStampValidationInterval` (1 minute, against the framework's 30-minute default) is used by both the cookie's `SecurityStampValidator` (static SSR requests; `SecurityStampValidatorOptions` in `Program.cs`) and `IdentityRevalidatingAuthenticationStateProvider.RevalidationInterval` (interactive circuits).
- Tests: `RoleChangeTests` (multi-role unions through the real handlers, policies and filters; grant/revoke/2FA-disable within one long-lived scope; stamp rotation; Student-only rule), `AccountPagesWiringTests.SecurityStamp_IsValidatedOnTheSameExplicitInterval_ForCookiesAndCircuits`.

## Staff who leave (FR-017, clarified 23/10/2026)

One rule, `src/Vlms.Infrastructure/Identity/LeftStaffPolicy.cs`, applied centrally (no per-page checks):

- **Staff roles stop counting.** For an `AppUser` with `HasLeft`, `IdentityCurrentUserContext.HasRole` returns false for Teacher, Admin and Safeguarding Officer (`LeftStaffPolicy.StaffRoleCounts`). Every policy, in-service role check and the staff arms of the `ConsentSensitiveDetails`/`DbsCheck` query filters read `HasRole`, so a leaver loses all staff access on their next action, even in an open circuit. Parent, Approver and Student roles still count.
- **Sign-in refused when nothing else is left.** `LeftStaffPolicy.IsLockedOut` = has left and holds no non-staff role. `VlmsUserConfirmation` treats such an account as unconfirmed; `VlmsSignInManager` maps that refusal to a plain failure (login page shows the generic "Invalid sign-in details.", checked before the password, so nothing is revealed), runs the pre-sign-in check before a recovery code (Identity's own `TwoFactorRecoveryCodeSignInAsync` does not), and requires `CanSignInAsync` on every security-stamp validation, which both the cookie validator and the circuit's `IdentityRevalidatingAuthenticationStateProvider` (now delegating to the sign-in manager) use. `AccountEmailService.RequestPasswordResetAsync` sends no link to a locked-out account.
- **Staff who are also parents** sign in as parents only. Parent-side checks that exclude leavers (`ConsentSensitiveDetails` parent arm, `ParentConsentService`, `StudentAccountService`, `CertificateAccessService`, `GuardianNotificationService`, `ConsentNotificationService`) treat a leaver who holds a staff role row as a parent who has not left, because their `HasLeft` records leaving the staff.
- **Role rows are kept** as history and as the marker that tells a staff leaver from a parent who left; `RoleAssignmentService.RevokeAsync` refuses to remove a staff role from a leaver (non-staff roles, such as Approver, can be removed). The last-Admin guards in `RevokeAsync` and `LeavingService.MarkStaffLeftAsync` count only Admins who haven't left; an Admin can't mark themselves as left.
- Tests: `LeftStaffLockoutEndToEndTests`, `LeavingServiceTests`, `SensitiveDataAccessControlTests` (real `IdentityCurrentUserContext`), `RoleAssignmentServiceTests`, `ParentConsentServiceTests` (TC-038).

## MFA enforcement (STATE.md "Identity" item 4)

TOTP multi-factor authentication is **enforced for `Role.Admin`/`Role.SafeguardingOfficer`/`Role.Teacher` specifically (Teacher added 22/10/2026, adr/0006 amendment, because Teachers read `ConsentSensitiveDetails`) — globally, for every authorized action, not just the safeguarding-sensitive pages — and merely offered (available to enrol, never required) for every other role (Parent, Student, Approver).** "Globally" is deliberate: a caller who holds Admin, SafeguardingOfficer or Teacher at all is blocked from every policy-gated page/resource until MFA is enabled, even a page a different role they also hold would otherwise satisfy on its own — the simpler, more conservative rule to state ("if you hold a safeguarding-sensitive role, MFA is mandatory, full stop") rather than "MFA is required only on the specific policy that happens to need that role today".

Two enforcement points, defense-in-depth, matching this codebase's existing "not just page-level gating" discipline:

- **Page/resource layer**: `MfaRequirement`/`MfaRequirementHandler` (`src/Vlms.Infrastructure/Authorization/`) — added to *every* policy in `Program.cs`'s `AddAuthorization` block (all six `Require{Role}` policies, `StudentAccess`, `RequireAdminOrTeacher`, `RequireAdminOrSafeguardingOfficer`), not just the Admin/SafeguardingOfficer-specific ones. `MfaRequirementHandler` succeeds unless the caller holds Admin, SafeguardingOfficer or Teacher without `ICurrentUserContext.HasMfaEnabled`.
- **Data layer**: `VlmsDbContext`'s `HasQueryFilter` on `DbsCheck` reads `(_currentUser.HasRole(Role.Admin) || _currentUser.HasRole(Role.SafeguardingOfficer)) && _currentUser.HasMfaEnabled`; the `ConsentSensitiveDetails` filter has that arm plus a Teacher arm that also requires `HasMfaEnabled`, and a linked-Parent arm without it (adr/0006) — see [access-control.md](access-control.md). Without this, an Admin/SafeguardingOfficer who never enrolled MFA could still be blocked from the `/safeguarding/*` pages by the handler above yet still read these entities through any other code path querying `VlmsDbContext` directly.

`Manage/TwoFactorAuthentication.razor`/`Manage/EnableAuthenticator.razor` (both under `src/Vlms.Web/Components/Account/Pages/`) are the enrolment pages — gated by a plain `[Authorize]` (any signed-in user), **not** an `MfaRequirement`-carrying policy, deliberately: gating the enrolment page itself behind an MFA requirement would be a lockout catch-22 for the exact roles that need it. A refused page shows `Routes.razor`'s not-authorised message, which links to the enrolment page; login itself does not redirect there. `EnableAuthenticator.razor` shows only the manual "enter this key" shared secret, not a scannable QR code — a documented scope decision (no built-in .NET QR encoder; a third-party rendering library was judged more new dependency than this "fewest moving parts" project takes on for what the manual key already achieves) — see its own doc comment.

## Guardian invite issuance (STATE.md "Identity" item 5)

Replaces the Microsoft Graph guardian-invitation mechanism (`docs/design/data-design.md`'s "Guardian link verification" section) with a self-rolled signed, single-use, expiring invite link — full design in [guardian-links.md](guardian-links.md) and the `GuardianInvite`/`GuardianInviteService` doc comments. In outline: `GuardianLinkService` calls `GuardianInviteService.IssueAsync` immediately after creating a `StudentGuardianLink`, whenever the target `ParentGuardian.AppUserId` is still null; the emailed link carries an ASP.NET Core Data Protection `ITimeLimitedDataProtector`-protected token (not a bespoke HMAC scheme — verified against Microsoft's own Data Protection consumer-API docs); `Components/Pages/Guardianship/AcceptInvite.razor` validates the token, calls `GuardianInviteService.AcceptAsync` (which creates the account via `AppUserProvisioningService` and marks the invite consumed, atomically), then signs the new guardian in directly via `SignInManager` — a step that must live in `Vlms.Web`, not Infrastructure, since it needs `HttpContext` to write the auth cookie.

## Curriculum-management policies

`RequireTeacher`/`RequireApprover` (both plain role policies, generated by the `foreach (var role in Enum.GetValues<Role>())` loop above) gate pages by role; the lesson suggestion pages use `RequireLessonSuggester` (Teacher or Approver) and `RequireLessonHistory` (Approver or Admin) — see [curriculum.md](curriculum.md) and [web.md](web.md). `LessonSuggestionService` also re-checks the caller's role itself (defense in depth, not solely UI-level gating) — see curriculum.md.

## Multi-role policy: `AnyRoleRequirement`/`AnyRoleAuthorizationHandler`

The single-role machinery above (`RoleRequirement`/`RoleAuthorizationHandler`, one `RequireX` policy per `Role` value) can't express "Admin OR Teacher", needed for the guardian-links page (FR-004). Added `AnyRoleRequirement` (params `Role[]`, constructor-guarded against an empty list) and `AnyRoleAuthorizationHandler` (`src/Vlms.Infrastructure/Authorization/`) — additive, registered alongside `RoleAuthorizationHandler` in `Program.cs`, wired to a new `"RequireAdminOrTeacher"` policy. See [guardian-links.md](guardian-links.md).

The same `AnyRoleRequirement`/`AnyRoleAuthorizationHandler` machinery also backs a second policy, `"RequireAdminOrSafeguardingOfficer"` (`Program.cs`), gating the consent/DBS management pages — matches the `VlmsDbContext` query filter on `DbsCheck`/`ConsentSensitiveDetails` exactly. See [safeguarding-consent.md](safeguarding-consent.md).

## Role assignment and first-Admin bootstrap

- **`RoleAssignmentService`** (`src/Vlms.Infrastructure/Identity/`) — the only code in `Vlms.Web` that writes/deletes `UserRole` rows. Admin-only inside the service on every method (`ListUsersAsync`/`GrantAsync`/`RevokeAsync`). Refuses to revoke the last Admin (self-lockout guard), refuses any grant to a leaver (`AppUser.HasLeft`), and throws on a duplicate grant or a revoke of a role not held. Page: `Components/Pages/Administration/UserRoles.razor` (`/administration/user-roles`, `RequireAdmin`), linked from `Home.razor`.
- **`FirstAdminBootstrapService`** — promotes an *existing* account (registered via `/Account/Register`) to Admin by email, case-insensitively, and only while no Admin exists; after that it is inert. Takes no `ICurrentUserContext`: its authorization is "no Admin exists" plus shell access to the server. Wired only into `Vlms.Jobs` (`dotnet Vlms.Jobs.dll bootstrap-admin <email>` — `deploy/README.md` §6a), never `Vlms.Web`; `FirstAdminBootstrapWiringTests` fails the build if `Vlms.Web` ever references it.
- **Waiting for approval** — `ListAwaitingApprovalAsync` lists accounts with no roles that aren't leavers, flagging those created by accepting a guardian invite (`GuardianInvite.ConsumedByAppUserId`) and naming their linked students; `ApproveGuardianAsParentAsync` grants `Parent` to an invite-created account only (self-registrations get a role through the general grant). Shown as the "Waiting for approval" section at the top of `/administration/user-roles`.
- **Guardian invite acceptance still grants no role.** A guardian who accepts an invite gets an account with zero roles until an Admin grants `Parent` on the role-assignment page — by design: Philip decided (11/10/2026) that an Admin approves every guardian, rather than acceptance granting `Parent` automatically (`docs/requirements/functional.md` FR-004).
- Both services are in `build/check-access-control.ps1`'s hashed set and have test-count floors there.

## Student sign-ins (FR-011, `docs/adr/0007-student-sign-in-accounts.md`)

- **`StudentAccountService`** (`src/Vlms.Infrastructure/Identity/`) — a linked, non-leaver Parent creates a student's sign-in (username and password, **no email**); that parent or an Admin with MFA resets it. The only code that grants `Role.Student` or sets `Student.AppUserId`; creation is one transaction (Identity row, `AppUser` with `Email = ""`, `UserRole`, conditional `Student.AppUserId` update). Pages: `/parent/student-sign-ins` (linked from `/parent/dashboard`), `/administration/student-sign-ins`.
- **`VlmsUserConfirmation`** replaces Identity's `DefaultUserConfirmation` (`AddUserConfirmation<T>()` in `Program.cs`): an account with `VlmsIdentityUser.SignInDisabled` set is never confirmed; an account with an email must have it confirmed (unchanged); an emailless account is confirmed only when a `Student` row points at it. `RequireConfirmedAccount` stays true.
- **What a student account is:** an account with no email (`StudentSignInPolicy.IsStudentAccount`). The password rule, the cookie rule and confirmation all use this one test.
- **Passwords (`VlmsPasswordValidator`, registered by `.AddVlmsPasswordRules()`, which replaces Identity's default validator):** adults go through Identity's own `PasswordValidator<T>` with the default options, unchanged; students need 8+ characters and nothing else.
- **Stay signed in (`VlmsSignInManager`, `Vlms.Web/Components/Account/`, registered by `.AddSignInManager<VlmsSignInManager>()`):** overrides `SignInWithClaimsAsync` so a student sign-in is always persistent with `ExpiresUtc` 90 days out (`StudentSignInPolicy.PersistentSignInLifetime`); sliding expiry keeps that span on renewal. Adults keep their Remember me choice and the handler's default lifetime. `Program.cs` sets `SlidingExpiration = true` and `SecurityStampValidatorOptions.ValidationInterval` (`VlmsIdentityPolicy.SecurityStampValidationInterval`, 30 minutes) explicitly.
- **Reset** (`StudentAccountService.ResetPasswordAsync`) rotates the stamp and clears lockout and the failed count, in one transaction. **Disable/restore** (`DisableSignInAsync`/`RestoreSignInAsync`, Admin with MFA) set or clear `VlmsIdentityUser.SignInDisabled` (`asp_net_users.sign_in_disabled`, migration `AddStudentSignInDisabled`) and rotate the stamp in the same update. A reset never touches the flag. Leaving doesn't disable. The flag lives on the Identity row, not `Student`, because `Student` updates copy every property with `SetValues` and would clear an unknown field.
- **`StudentUsername`** — 3–32 of `[A-Za-z0-9._-]`, never `@`; adult provisioning now refuses an email without `@`, so usernames can't collide.
- `RoleAssignmentService.GrantAsync` refuses `Student`, and any role to a student sign-in.
- Login's field is "Email or student username" (no email validation). Forgot/reset-by-email can't reach a student (no email).
- **`StudentPageService`** + `/student` (`RequireStudent`): resolves the caller's own record, reusing `StudentRosterService.LoadRecordAsync`.
