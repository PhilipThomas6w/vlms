# Data access: VlmsDbContext

`src/Vlms.Infrastructure/VlmsDbContext.cs`. One `DbSet<T>` per entity in [domain.md](domain.md); `OnModelCreating` configures every relationship via Fluent API. Design source: `docs/design/data-design.md`.

## Conventions to preserve

- **All keys are application-assigned** (`ValueGeneratedNever`), except `SensitiveDataAccessLog.Id` and `VlmsIdentityUser.Id` (both `ValueGeneratedOnAdd` — the latter is ASP.NET Core Identity's own store row, not a `Vlms.Domain` entity; `AppUser.Id` is then copied in from it, not computed independently — see [domain.md](domain.md)/[authentication-authorization.md](authentication-authorization.md)). This was a deliberate choice for determinism in the access-control tests (see the `OnModelCreating` comment) — don't "fix" it to database identity without checking what depends on the current behaviour (`GuardianInviteService`/`GuardianLinkService`'s own `MaxAsync + 1` patterns, for instance).
- **Two entities carry `HasQueryFilter`**: `ConsentSensitiveDetails` and `DbsCheck`. See [access-control.md](access-control.md) before adding, removing, or modifying any query filter in this file — this is the one part of the schema with the most design-review scrutiny behind it.
- **`SensitiveDataAuditInterceptor.Instance`** is registered in `OnConfiguring` via `AddInterceptors`. It's a singleton (see [access-control.md](access-control.md) for why that's safe).
- **`ConsentRecord` ↔ `ConsentSensitiveDetails`** is 1:1, FK on the dependent (`ConsentSensitiveDetails.ConsentRecordId`), cascade delete. **`LessonChangeProposal.ResubmissionOfProposalId`** is a self-referencing FK (restrict delete) supporting the propose → reject-with-comments → resubmit workflow.
- **Every table and column name is snake_case** (`src/Vlms.Infrastructure/Naming/SnakeCaseNamingConvention.cs`, applied once at the very end of `OnModelCreating`) — PostgreSQL's own idiomatic identifier convention, per adr/0005-hosting-pivot-self-hosted-vps-postgresql.md's "confirm/apply this repo's chosen casing convention" instruction. Table names come from the PascalCase default EF Core assigns from each `DbSet<T>` property (e.g. `SensitiveDataAccessLogs`), snake_cased to `sensitive_data_access_logs` — plural, not the singular `sensitive_data_access_log` ADR-0005 used only as a non-binding illustrative example, chosen to stay consistent with every other table's pluralized naming rather than introduce a singular/plural split. Primary key/foreign key/index **constraint names are deliberately left at EF Core's PascalCase defaults** (e.g. `PK_ranks`, `FK_dbs_checks_app_users_teacher_user_id` — note these already incorporate the renamed table/column names) — a scoped decision, not an oversight, since they're internal and essentially never typed by hand. Hand-rolled rather than the third-party `EFCore.NamingConventions` package, matching this repo's "fewest moving parts" pattern (adr/0003) for a ~30-line mechanical rename; correctly handles this schema's one real acronym case (`ConsentSensitiveDetails.DietarySEN` -> `dietary_sen`, not `dietary_s_e_n`) — see its own tests, `tests/Vlms.Tests/Infrastructure/SnakeCaseNamingConventionTests.cs`.

## Migrations (`src/Vlms.Infrastructure/Migrations/`)

**Regenerated from scratch twice** — once for the PostgreSQL provider switch (adr/0005), and again for STATE.md's "Identity" item (Microsoft Entra External ID → self-rolled ASP.NET Core Identity), which changed `AppUser` (dropped `EntraObjectId`) and added `GuardianInvite`/Identity's own store tables to the model. This is still a pre-production codebase with no live database anywhere holding applied migration state (confirmed from STATE.md before regenerating either time, not assumed), so the squash-to-two-migrations convention holds rather than accumulating incremental migrations. Superseded migrations' intent and full history remain recorded in ADR-0004 §4/Alternatives, which no regeneration re-enacts.

- `20260720171330_InitialCreate` — the 17 `Vlms.Domain` entities ([domain.md](domain.md)) plus ASP.NET Core Identity's own store tables (`AspNetUsers`/`AspNetUserClaims`/`AspNetUserLogins`/`AspNetUserTokens`, snake_cased like everything else — from `IdentityUserContext<VlmsIdentityUser, int>`'s own model configuration, called via `base.OnModelCreating` — see [authentication-authorization.md](authentication-authorization.md)), ADR-0004's query-filter/interceptor mechanism included from the start, same as the migration sets it replaces.
- `20260720181357_RevokeUpdateDeleteOnSensitiveDataAccessLog` — pure DDL, no entity/model changes: `REVOKE UPDATE, DELETE ON sensitive_data_access_logs FROM PUBLIC` — the one-migration net effect of the two superseded SQL Server DENY migrations, per this item's own instruction not to replay that two-step history. **Read the migration's own doc comment before assuming this is DENY's equivalent — it verifiably isn't**: see [access-control.md](access-control.md)'s "Tamper protection" section for the full, checked-against-current-PostgreSQL-docs explanation of why REVOKE-from-PUBLIC is structurally weaker than SQL Server's DENY-to-public, and what the residual real protection depends on. Regenerating `InitialCreate` above (an empty scaffold, since this migration's `REVOKE` is raw SQL the EF model diff can't produce) meant re-pasting this migration's Up/Down body and doc comment by hand each time — a real trap for a future regeneration to repeat unless the doc comment is read first.
- `20260811231909_AddLeavingFieldsToStudentAndAppUser` — STATE.md "Manual 'leaving' flag for students and teachers": adds `students.left_at` (nullable) and `app_users.has_left`/`app_users.left_at` (non-nullable bool defaulting `false` / nullable) — see [domain.md](domain.md)'s entity notes and [admin-reporting.md](admin-reporting.md)'s "Records due for deletion" section for what sets them and how `RetentionFlagging` now uses them. Pure additive columns on two non-restricted entities — no data migration needed, every existing row defaults to "not left".

`VlmsDbContextFactory` (`src/Vlms.Infrastructure/VlmsDbContextFactory.cs`) is the EF Core design-time factory used by `dotnet ef` tooling — it has no request context, so it uses `NullCurrentUserContext`. `dotnet ef migrations has-pending-model-changes` (run by the maker/checker cycle, not currently a `build/verify.ps1` stage) is the way to catch model/migration drift; consider wiring it into `verify.ps1` if migrations become a frequent source of drift.

## Provider split: PostgreSQL (production) vs SQLite (tests)

`VlmsDbContext.OnConfiguring` doesn't choose a provider — that's done by whoever constructs the `DbContextOptions`. `Vlms.Web/Program.cs` and `Vlms.Jobs/Program.cs` use `UseNpgsql` (adr/0005-hosting-pivot-self-hosted-vps-postgresql.md — supersedes the original `UseSqlServer`); tests use SQLite in-memory, unchanged by the provider swap. See [testing.md](testing.md) for why, for the explicit test-provider-strategy decision this pivot required, and for a caveat about SQLite's connection-sharing behaviour under this context's own "open a second context" patterns.
