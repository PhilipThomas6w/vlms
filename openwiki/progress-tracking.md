# Progress tracking

Design source: `docs/design/low-level-design.md` "CompletionService"/"PromotionService"/"CertificateService", `docs/design/data-design.md`, `docs/requirements/functional.md` (FR-003, TC-001/TC-003). Implements VISION.md's second mission sentence: lesson completions, auto-promotion through the rank ladder, and auto-generated PDF certificates.

All three services live in `src/Vlms.Infrastructure/Progress/` — despite low-level-design.md heading this section "Key domain services (Vlms.Domain)", they're built in Infrastructure because they depend on `VlmsDbContext`/EF Core, the same divergence already established by `LessonProposalService` (see [curriculum.md](curriculum.md)). `Vlms.Domain` stays EF-Core-free.

## `CompletionService.MarkCompleteAsync(studentId, lessonId, note?)`

Teacher-only (role-checked inside the service — same defense-in-depth pattern as `LessonProposalService`, see [curriculum.md](curriculum.md)). Steps:

1. **Consent gate (functional.md FR-003, data-design.md):** blocked with `InvalidOperationException` unless the student has at least one `ConsentRecord` with `Status == Approved` and `ExpiryDate >= today`. Reads only the non-sensitive `ConsentRecord` (`Status`/`ExpiryDate`) — never `ConsentSensitiveDetails`, which this service has no reason to touch (see [access-control.md](access-control.md)). This check is computed fresh from `ConsentRecord` every call, not from any stored "expired" flag — so `ConsentExpiryJob` (see [safeguarding-consent.md](safeguarding-consent.md)) doesn't need to write anything for blocking to keep working; it only makes the same population visible to Admin/Safeguarding Officer ahead of time.
2. Records the `StudentLessonCompletion` row.
3. Calls `PromotionService.CheckAndPromoteAsync` (order matches low-level-design.md's literal wording: "triggers PromotionService check and CertificateService.Generate(...)").
4. Calls `CertificateService.GenerateAsync` for the new completion — data-design.md: a `Certificate` is generated **per completion**, not just per promotion (`StudentLessonCompletion` 1:1 `Certificate`).

**Not wrapped in one explicit database transaction** across all three steps — each service `SaveChanges()`s its own work. A deliberate simplification (VISION.md "fewest moving parts" for a solo-maintained, tens-of-users system): a failure partway (e.g. a blob upload failing) leaves the completion recorded but the certificate/promotion step incomplete, recoverable by re-running rather than something that corrupts state.

## `CompletionService.ReverseAsync(completionId, note?)`

Teacher self-correction (functional.md: "can self-correct/reverse their own entry (e.g. within some reasonable window) — no separate correction gate through Admin"). Closes the gap this file used to name explicitly ("`IsReversed`/`ReversedAt` exist on the entity and are read by `PromotionService`/`ProgressReportingService`/`AtRiskStudentFlagging`/`ParentDashboardService`, but nothing in `src/` ever sets them — only test seed data does").

Four scope decisions, each made explicitly rather than left implicit or guessed:

1. **Own entry only, not any Teacher's.** functional.md says "their own entry" — narrower than low-level-design.md's "a Teacher sees all students in the programme... not scoped to `AssignedTeacherUserId`" (that's about which *students* a Teacher may act on at all, not who may undo one already-made completion). Only the Teacher recorded in `StudentLessonCompletion.CompletedByUserId` may reverse it; any other Teacher gets `UnauthorizedAccessException`, with no mutation.
2. **A bounded time window is enforced.** functional.md's "e.g. within some reasonable window" names no figure but implies a limit exists. `CompletionService.DefaultReversalWindowDays = 7` — a documented build-time default, the same "configurable, no number given" situation `ConsentExpiryJob.DefaultExpiryWarningWindowDays`/`NotificationService.DefaultSafeguardingCriticalMaxAttempts` already resolved for this codebase (see [safeguarding-consent.md](safeguarding-consent.md)/[notifications.md](notifications.md)). Reasoning: long enough to cover "caught at the next session", short enough to stay genuine self-correction rather than a general undo button that could quietly rewrite the "who received what and when" audit trail functional.md's own Progress-tracking section asks certificates/badges to give. Configurable via the constructor.
3. **The optional-note stance carries over from completion, not tightened.** functional.md frames the note as "available but optional (low friction, not a mandatory audit gate)" and wants "no separate correction gate through Admin" — a mandatory reversal reason would itself be exactly that kind of gate. There is one `Note` field per completion, not a separate reversal-note column (data-design.md names only one); a supplied reversal reason is appended to whatever the completion's existing note already said, as a `"{original}\nReversed: {reason}"` line (or just `"Reversed: {reason}"` if there was no original note) — never overwritten.
4. **Does not cascade to a past promotion.** `PromotionService.CheckAndPromoteAsync` already excludes reversed completions from *future* rank-progression counting (unchanged). Whether reversing a completion that already contributed to a promotion that already happened should retroactively un-promote the student — and, transitively, un-award any badge and undo further progress made since — is a materially bigger question neither `data-design.md` nor `low-level-design.md` asks for; explicitly out of scope, the same narrowly-scoped-effect precedent the certificate-visibility decision (STATE.md, 2026-07-20, see [parent-dashboard.md](parent-dashboard.md)) already set for this exact field.

Rejects an unknown `completionId` via `SingleAsync` (this codebase's existing convention) and an already-reversed completion with a clear `InvalidOperationException`.

**Page:** `src/Vlms.Web/Components/Pages/Progress/CompletionReversals.razor` (`/progress/completions`), gated `[Authorize(Policy = "RequireTeacher")]`, linked from `Home.razor`. Lists the caller's own recorded completions (`StudentLessonCompletion.CompletedByUserId == caller`, most recent 50), with a "Reverse" action per not-yet-reversed row that opens an inline form for the optional reason. This is the first UI consumer of `CompletionService` — see `IBlobStorage`'s section below for what that triggered wiring into `Program.cs`.

## `PromotionService.CheckAndPromoteAsync(studentId)`

Called by `CompletionService` after every completion (no role check of its own — it's a system-internal step following an already-authorized `MarkCompleteAsync` call). Returns `true` if the student was promoted or graduated, `false` if their current rank still has incomplete active lessons — the definition-of-done "non-promotion case".

- **Completion test:** every `Lesson` with `RankId == student.CurrentRankId && IsActive` must have a non-reversed `StudentLessonCompletion` for that student. A rank with zero active lessons is vacuously "complete" (unusual in practice, not specifically guarded against). Reversed completions (`IsReversed == true`) never count.
- **Ladder ordering:** `Rank.Order` (already on the entity, with the existing `Rank.IsBefore` helper) — "next rank" = the `Rank` with the smallest `Order` greater than the current one. No schema gap here — `Order` already fully describes the ladder.
- **On promotion:** closes the current `StudentRankProgress` row (sets `CompletedAt`), opens a new one for the next rank, advances `Student.CurrentRankId`, and awards that (just-completed) rank's `RankBadge` via a new `StudentBadge` — if no `RankBadge` is configured for that rank, promotion still proceeds with no badge (badge reference data is populated separately, e.g. by an Admin; its absence must not block a student's progression).
- **At the final rank** (no `Rank` with a higher `Order`): sets `Student.Status = Graduated` instead of advancing; `CurrentRankId` is left unchanged.
- **Precondition — flagged, not silently patched over:** this service expects an *open* `StudentRankProgress` row (`CompletedAt == null`) to already exist for the student's current rank before it's ever called, and throws a clear `InvalidOperationException` if none is found rather than fabricating one. **Closed:** `StudentRegistrationService` (see [student-registration.md](student-registration.md)) now opens exactly this row at registration; `PromotionServiceTests` still seed the row directly (unit-test isolation), while `StudentRegistrationServiceTests` has a dedicated integration test proving a freshly registered student can actually be driven through `CheckAndPromoteAsync` without hitting this exception.

## `CertificateService.GenerateAsync(completionId)`

Builds a minimal QuestPDF document (student name, lesson title, completion date), uploads it via `IBlobStorage` under `certificates/{studentId}/{completionId}.pdf`, and writes the `Certificate` row. `QuestPDF.Settings.License = LicenseType.Community` is set once in a static constructor — independent of whether `Vlms.Web`'s `Program.cs` ever touches this class, so it's set correctly regardless of call site (mirrors the "process-wide, set-once" nature of a licence flag). No role check of its own, same reasoning as `PromotionService`.

## `IBlobStorage` (`src/Vlms.Domain/IBlobStorage.cs`)

Abstraction, same placement pattern as `ICurrentUserContext`: the interface lives in `Vlms.Domain` (technology-agnostic, no storage-SDK dependency), both implementations live in `Vlms.Infrastructure`:

- **`Storage/LocalDiskBlobStorage.cs`** — real implementation, writing to the local filesystem under a configurable root directory (`LocalDiskBlobStorage.DefaultRootPath = "App_Data/blobs"` when none is supplied). Superseded the original `Storage/AzureBlobStorage.cs` (backed by `Azure.Storage.Blobs`, adr/0001-technology-stack.md) per adr/0005-hosting-pivot-self-hosted-vps-postgresql.md — certificates/lesson assets now live on the self-hosted VPS's own disk; the `Azure.Storage.Blobs` package reference was removed from `Vlms.Infrastructure.csproj` in the same commit. Handles the real-filesystem concerns an in-memory fake doesn't need to: creates the target directory (and any missing parent directories) on upload, and rejects a blob key that could otherwise escape the configured root — absolute paths, `.`/`..` path segments, or a key containing a drive-letter-style colon — with an `ArgumentException`, checked both by rejecting the offending segment explicitly *and*, as defense in depth, by confirming the fully-resolved path still lands inside the root before any file write. Today's only real caller (`CertificateService`, below) always passes a well-formed, internally-generated key (`certificates/{studentId}/{completionId}.pdf`), but `IBlobStorage.UploadAsync`'s contract accepts any string, so this defense is real rather than decorative. **Now wired into `Vlms.Web`'s DI container and `appsettings.json`** (STATE.md "Teacher-facing reverse a completion flow" — `Progress/CompletionReversals.razor` is the first UI consumer of `CompletionService`, which is exactly the moment this section previously named as the trigger to finally wire this in): `Program.cs` registers `IBlobStorage`/`PromotionService`/`CertificateService`/`CompletionService` as scoped services; `appsettings.json`'s new `"Storage:LocalRootPath"` key (defaulting to `App_Data/blobs` when absent/blank, same as the class's own `DefaultRootPath`) is the config path. Off-box backup of this directory to an S3-compatible object store (Cloudflare R2 vs Backblaze B2, adr/0005) remains a still-undecided separate concern, not built here.
- **`InMemoryBlobStorage`** (`tests/Vlms.Tests/Infrastructure/InMemoryBlobStorage.cs`) — the test double, same spirit as `FakeCurrentUserContext`. Records every uploaded blob's bytes so tests can assert on what was actually written (including checking the `%PDF` magic-byte header — proof QuestPDF produced a real document, not placeholder bytes). `LocalDiskBlobStorage` itself is tested separately and directly, against a real per-test temp directory — see `tests/Vlms.Tests/Infrastructure/LocalDiskBlobStorageTests.cs` and [testing.md](testing.md).

## Tests

`tests/Vlms.Tests/Infrastructure/CompletionServiceTests.cs`, `PromotionServiceTests.cs`, `CertificateServiceTests.cs` — same SQLite-in-memory-via-DI pattern as `LessonProposalServiceTests` (see [testing.md](testing.md)). Coverage includes: completion recording with active consent (and the resulting certificate), expired-consent and missing-consent blocking, non-Teacher denial, promotion on final-lesson completion, the non-promotion case (incomplete lessons), reversed completions not counting, badge award with/without a configured `RankBadge`, graduation at the final rank, and certificate generation including the PDF magic-byte check and an unknown-completion-id failure.

`ReverseAsync` coverage in `CompletionServiceTests.cs`: success (sets `IsReversed`/`ReversedAt`, merges the reversal note correctly with/without an existing note), denial for a different Teacher (no mutation), denial for every non-Teacher role (no mutation), already-reversed rejection, unknown-`completionId` rejection, inside/outside the default 7-day window, and a test proving the window is genuinely configurable (a 1-day window rejects what a 30-day window accepts, for the same completion). **The property that actually matters** (STATE.md's own framing, closing the loop its gap description named): `ReverseAsync_ThenCompletingRemainingLesson_DoesNotTriggerPromotion_UntilReversedLessonIsRedone` drives a completion through the real reversal write path (not seed data) and proves `PromotionService` genuinely excludes it — complete lesson 1, reverse it, complete lesson 2 (no promotion, since only 1 of 2 active lessons has a non-reversed completion), then re-complete lesson 1 (now promotes). The equivalent property is also proven for the other two `IsReversed` consumers, each via a genuine `ReverseAsync` call rather than seeded `IsReversed = true`: `ProgressReportingServiceTests.GetProgressStatsAsync_TotalLessonCompletions_DropsAfterGenuineReversal_ViaCompletionServiceReverseAsync` and `ParentDashboardServiceTests.GetDashboardAsync_CertificateHiddenAfterGenuineReversal_ViaCompletionServiceReverseAsync` (see [parent-dashboard.md](parent-dashboard.md)). `AtRiskStudentFlagging` was not given an equivalent genuine-reversal test — its `!c.IsReversed` filter is identical code to `PromotionService`'s and `ProgressReportingService`'s (same field, same negation), and the DRY-extraction equivalence test already proves it and `ProgressReportingService.GetAtRiskStudentsAsync` share one implementation — so `PromotionService`'s genuine-reversal test already covers the underlying mechanism this filter also relies on.

`tests/Vlms.Tests/Infrastructure/LocalDiskBlobStorageTests.cs` — direct tests of `LocalDiskBlobStorage` against a real, per-test temp directory (no DB/DI involved): round-trip write/read of the exact bytes, key-with-slashes scoping to the matching nested path, automatic creation of a not-yet-existing nested directory, overwrite-on-reupload, and rejection (with nothing written) of `..`/`.`-segment and absolute-path keys, plus a blank-key rejection.
