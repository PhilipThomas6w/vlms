# Data Design

Status: in progress

Relational model in self-hosted PostgreSQL, accessed via EF Core/Npgsql (see `adr/0001-technology-stack.md` as amended by `adr/0005-hosting-pivot-self-hosted-vps-postgresql.md`, which replaced the originally-specified Azure SQL Database). Table and column names use snake_case, PostgreSQL's own idiomatic identifier convention (see `openwiki/data-access.md`). Entities below supersede the prior build's Dataverse model — retained conceptually where still valid, revised where discovery resolved an ambiguity (certificates and badges are now first-class tracked entities, not implicit).

## Relationships (summary)

- `Rank` 1:N `Lesson`, 1:N `RankBadge`.
- `Lesson` 1:N `LessonSuggestion`, 1:N `LessonVersion`, 1:N `StudentLessonCompletion`.
- `Student` 1:N `StudentLessonCompletion`, 1:N `StudentRankProgress`, 1:N `StudentBadge`, 1:N `ConsentRecord`; N:N `ParentGuardian` via `StudentGuardianLink`.
- `ConsentRecord` 1:1 `ConsentSensitiveDetails` (the entity split described above).
- `StudentLessonCompletion` 1:1 `Certificate` (nullable until generated).
- `AppUser` 1:N `UserRole`; referenced by `Student.AssignedTeacherUserId`, `Student.AppUserId` (self-login), `ParentGuardian.AppUserId` (parent-login), `LessonSuggestion.AuthorUserId`/`DecidedByUserId`, `LessonVersion.ApprovedByUserId`/`PublishedByUserId`, `StudentLessonCompletion.CompletedByUserId`, `ConsentRecord.ApprovedByUserId`, `DbsCheck.TeacherUserId`.

## Sensitive-entity access restriction (corrected at second design review)

Per `governance/security-compliance.md` (UK GDPR/DPA 2018, special-category + children's data) and `adr/0004-sensitive-data-access-control.md`:

- **Design correction:** the first pass at this design specified column-level masking of three `ConsentRecord` fields via an EF Core global query filter. That doesn't work: a global query filter is a row-inclusion predicate — it can only include or exclude an entire row, not redact individual columns within a row a role otherwise needs (Teacher must read `ConsentRecord.Status`/`ExpiryDate`). Fixed by splitting the sensitive fields into their own entity, `ConsentSensitiveDetails` (see Entities table), so the *same* whole-entity filter pattern that correctly restricts `DbsCheck` now also correctly restricts the sensitive consent fields.
- `DbsCheck` (whole entity): visible only to Admin and Safeguarding Officer. Teacher and Approver have no access.
- `ConsentSensitiveDetails` (whole entity, containing what were the `EmergencyMedicalInfo`/`DietaryRequirements`/`SpecialEducationalNeeds`/`EmergencyContact` fields): visible only to Admin and Safeguarding Officer. Teacher and Approver can still read the (now separate) `ConsentRecord` row for `Status`/`ExpiryDate`.
- The Approver role's remit is curriculum/lesson-change approval only (`LessonSuggestion.DecidedByUserId`, `LessonVersion.ApprovedByUserId`) — it has no involvement in consent or DBS approval, and no elevated PII access beyond a regular Teacher.
- **Enforcement mechanism:** EF Core global query filters on `DbsCheck` and `ConsentSensitiveDetails`, configured on the `DbContext`, keyed by the current caller's role. A developer cannot accidentally leak either entity by writing a new query or report without explicitly bypassing the filter (`IgnoreQueryFilters()`), which is a deliberate, greppable, reviewable act. See [EF Core global query filters](https://learn.microsoft.com/ef/core/querying/filters).

## Audit logging of sensitive-data reads

- Every read of a `DbsCheck` or `ConsentSensitiveDetails` row writes a `SensitiveDataAccessLog` row (who, what, when). This is a genuine control gap identified at design review — the prior model only logged who *created/approved* a record, not who subsequently *viewed* it. Given the entire justification for managing this data in-system is safeguarding, an access log is not optional.
- **Write mechanism (corrected at third design review):** an `IMaterializationInterceptor` registered on the `DbContext` (see `adr/0004-sensitive-data-access-control.md`) — its `InitializedInstance` hook fires once per entity EF materializes from a query, giving direct typed access (`entity is DbsCheck dbs → log dbs.Id`) without SQL text-matching or manual reader handling, and correctly per row even across EF's compiled-query cache. This is structural — it applies to every query against these tables regardless of call site — rather than a per-repository convention a future developer could forget. (A prior version of this ADR named `DbCommandInterceptor` instead; that mechanism operates on raw SQL and can't reliably extract a typed `EntityId`, so it was corrected.)
- **Tamper protection (added at second design review; mechanism re-implemented for PostgreSQL by `adr/0005-hosting-pivot-self-hosted-vps-postgresql.md`):** `SensitiveDataAccessLog` has `UPDATE`/`DELETE` denied at the database permission level for this table specifically, not just an "append-only" convention in application code — originally SQL Server `DENY` on the application's database principal; now PostgreSQL `REVOKE UPDATE, DELETE ... FROM PUBLIC` plus Row-Level Security (`ENABLE`/`FORCE ROW LEVEL SECURITY` with no `UPDATE`/`DELETE` policy, closing the gap that `REVOKE` alone doesn't bind the table owner the way SQL Server's `DENY` does) — see `adr/0004-sensitive-data-access-control.md` §4/§6.
- **Retention (added at second design review):** audit log entries are retained **6 years** regardless of the referenced record's own retention period (matching the longer DBS retention bar, since the log's purpose is accountability, not the underlying record's lifecycle) — a deliberate choice for the owner to override if a different period is preferred.

## Guardian link verification

- **Amended 22/10/2026 (`adr/0008` answers 1 and 4):** parents now apply to register their own children (`StudentApplication`, above). The application is not a link: a `StudentGuardianLink` is created only when an Admin approves the application after a Safeguarding Officer's review, or when an Admin registers a child or links a guardian directly. Teachers no longer create links or register students (service checks and page policies are Admin only). The approving Admin's review of the application is the verification step below; the parent's ownership of their account is proved by being signed in, so no invite is issued. The original wording follows.

- A `StudentGuardianLink` is created **only by Admin (or a Teacher acting under Admin's authority) at student registration** — never by parent self-service. The Admin/Teacher enters the guardian's details; if the guardian doesn't already hold an account, this issues a self-rolled signed, single-use, expiring invite link (`GuardianInvite`, `adr/0005-hosting-pivot-self-hosted-vps-postgresql.md`) scoped to the correct `Student` record, emailed via SMTP — replacing what was originally planned as a Microsoft Entra External ID invitation. See `openwiki/guardian-links.md` for the as-built mechanism.
- **Evidentiary basis (added at second design review):** the Admin/Teacher creating the link should do so through the same channel already used to enrol the student (i.e. the guardian is who the family named at enrolment, or someone already known to the programme) — not a separate, formal identity-verification process. This is deliberately lightweight, proportionate to a small, personally-known membership, not a large anonymous user base.
- This closes a design-review gap: open self-service sign-up (this system still has a general `/Account/Register` page, for authentication only) would otherwise let a parent register and claim a relationship to a child with no verification that the claim is genuine, before ever touching medical/consent data — which is exactly why `StudentGuardianLink` creation itself is never self-service, regardless of how a guardian's account was created.

## Data ownership & lifecycle

- System of record: this database is authoritative for all entities above (no external source of truth, per `design/integration.md`).
- Retention/deletion policy (UK GDPR requirement): student records (including consent, medical/dietary/SEN data) retained **3 years from the student leaving/graduating** the programme. DBS (Disclosure and Barring Service, gov.uk) checks are held against Teachers, not students, and are retained **6 years** after expiry/the teacher leaving.
- Registration applications (`StudentApplication` and its restricted `StudentApplicationSensitiveDetails`: the consent form, medical/dietary/SEN details, the review exchange, the parent's phone and address): retained **1 year after the decision** (the Admin's final approval or rejection, or the Safeguarding Officer's rejection at stage 1), approved and rejected alike (Philip, 23/10/2026). Applications still under review are not flagged. An approved child's student and consent records follow the student rule above. Flagged on the "records due for deletion" report.
- **Deletion enforcement — decided (Philip, 27/10/2026; `adr/0014-retention-purge.md`):** an Admin confirms each deletion from the "records due for deletion" report (typing the person's name); a monthly email reminds the chapter's Admins while records are due; a student's deletion removes everything linked to them, and a parent's account goes with their last linked child unless they hold a staff role or have another child; each deletion is recorded in a deletion log without personal data; the read-audit log is purged automatically after 6 years by a dedicated database role. Built 27/10/2026: `Retention/RetentionDeletionService`, `RetentionReminderService`, `AuditLogPurgeService`; new national entity `DeletionLogEntry` (table `deletion_log`: record type, record id, deleted at, deleted by user id, chapter id; no foreign keys, append-only by REVOKE and forced row-level security; migration `AddDeletionLog`, which also adds the `vlms_retention` DELETE policy on `sensitive_data_access_logs`). A student's consent and application sensitive details are removed by the database's cascade without being read. An account still named by a kept record (for example a register taken, a lesson version) is kept, not deleted.
- **Hard delete vs anonymisation — decided (second design review):** hard delete. Simpler to reason about and implement solo, avoids the adequacy debate over whether an anonymisation technique genuinely prevents re-identification (a live UK GDPR concern), and nothing in the confirmed requirements needs retained-but-anonymised data for ongoing reporting/analytics. Owner can override if historical trend reporting turns out to matter later.
- No migration — clean start (confirmed, `raid.md` A-003).
