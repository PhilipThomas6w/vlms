# Low-Level Design

Status: in progress

## Solution structure

- `Vlms.Web` — the Blazor Web App (UI, Razor components, authorization policies).
- `Vlms.Domain` — entities (`data-design.md`), domain logic (promotion rules, lesson suggestion states).
- `Vlms.Infrastructure` — EF Core `DbContext` (Npgsql/PostgreSQL), self-rolled ASP.NET Core Identity wiring, local-disk file storage client, Microsoft Graph email client (`GraphEmailSender`), QuestPDF certificate generation.
- `Vlms.Jobs` — the scheduled-work console host (`ConsentExpiryJob`), invoked daily by a systemd timer on the self-hosted VPS, independent of `Vlms.Web` — see `adr/0003-scheduled-jobs-webjobs.md` as amended by `adr/0005-hosting-pivot-self-hosted-vps-postgresql.md`.
- `Vlms.Tests` — unit/integration tests (see `quality/test-plan.md`).

No separate public API project — per `design/integration.md`, VLMS is standalone with no external system needing programmatic access. If that changes, a `Vlms.Api` project can be split out later without redesigning the domain/infrastructure layers.

## Authorization model

- Authentication: self-rolled ASP.NET Core Identity (built-in TOTP MFA), per `adr/0001-technology-stack.md` as amended by `adr/0005-hosting-pivot-self-hosted-vps-postgresql.md` (originally Microsoft Entra External ID/OIDC).
- Authorization: role-based (`UserRole.Role` — Admin/Teacher/Approver/Parent/Student/SafeguardingOfficer) implemented as ASP.NET Core authorization policies, **plus** resource-based checks where a flat role isn't enough:
  - A Parent may only view/act on `Student` records linked to them via `StudentGuardianLink` — and that link is only ever created by Admin/Teacher (see `data-design.md` — Guardian link verification), never claimed by the parent themselves.
  - A Student may only view their own record.
  - A Teacher sees **all** students in the programme (confirmed) — not scoped to `Student.AssignedTeacherUserId`, so teachers can cover for each other. Since chapters (`adr/0010-chapters.md`), "the programme" is the Teacher's active chapter: every chapter role is held in a chapter and counts only in the chapter the person is working in, and the "Chapter" query filter limits every person-level entity to that chapter (plus a parent's own children). The National Administrator manages chapters, chapter Admins and national roles and sees no chapter's records.
- Whole-entity access restriction (`data-design.md`): `DbsCheck` and `ConsentSensitiveDetails` (the medical/dietary-SEN/emergency-contact fields, split out from `ConsentRecord` — see `adr/0004-sensitive-data-access-control.md` for why a query filter cannot mask individual columns) are restricted structurally via **EF Core global query filters** on the `DbContext`, not an opt-in per-call convention. `ConsentRecord` itself (status, expiry, non-sensitive flags) remains readable by Teacher/Approver, since `CompletionService` needs it to enforce the consent-blocks-completion rule. Every read of `DbsCheck`/`ConsentSensitiveDetails` is additionally written to `SensitiveDataAccessLog` via an `IMaterializationInterceptor` (`adr/0004`) — chosen over a raw-SQL `DbCommandInterceptor` because it gives direct typed access to the materialized entity's ID, correctly once per row.
- Test coverage for this model (whole-entity restriction, audit logging, guardian-link scoping) is the priority of the access-control test suite — see `quality/test-plan.md` TC-006/007/008 and TC-011/012.

## Key domain services (`Vlms.Domain`)

- **`LessonSuggestionService`** (`adr/0013`) — Teachers and Approvers save, submit and discard their own drafts (`SaveDraftAsync`, `SubmitAsync` with a required reason, `DiscardAsync`); only one Draft or Submitted suggestion per lesson (service check plus a filtered unique index); each draft records the version it is based on (`BaseVersionNumber`). Approvers list the queue (`GetQueueAsync`), review a suggestion as a word-level diff (`GetReviewAsync`, `LessonDiff` on DiffPlex), approve it (`ApproveAsync`, self-approval allowed, refused if its base is no longer the current version) or send it back with a required comment (`SendBackAsync`), or refer it to committee (`ReferAsync`, optional reason; only a submitted, current, unreferred suggestion), after which `ApproveAsync` refuses it and `ApproveReferredAsync` records one approval per Approver (the author's own counting) and publishes on the third, a unique index on (suggestion, place) turning a simultaneous approval into "reload and try again"; `CountAwaitingMyReviewAsync` gives the menu count (submitted suggestions not referred, or referred and not yet approved by the caller; zero for non-Approvers). `SubmitAsync` emails every Approver who has not left through `LessonSuggestionNotificationService` and `INotificationService`, after the save and never throwing; while the national setting allows it they publish at once (`PublishNowAsync`). Each approval or direct publish adds the next `LessonVersion` (kinds Converted, ApprovedSuggestion, PublishedDirectly, ReplacedInFull), updates the lesson's live body, title, order, tags and pictures, and changes its content version so saved offline copies refresh. Approvers and Admins read a lesson's history (`GetHistoryAsync`). National Administrators read and change the setting (`SetDirectPublishingAllowedAsync`), each change audited in `LessonPublishingSettingChange`. Pictures are uploaded into a draft through `UploadPictureAsync` (author only, alt text required) and served by `LessonSuggestionEndpoints`. Every method does its own role check. Replaces `LessonProposalService` (removed).
- **`CompletionService`** — `MarkComplete(studentId, lessonId, teacherUserId, note?)`: blocked if the student's active `ConsentRecord.Status`/`ExpiryDate` shows expired/missing consent (hard business rule, `functional.md`) — reads only the non-sensitive `ConsentRecord`, never `ConsentSensitiveDetails`; on success, triggers `PromotionService` check and `CertificateService.Generate(...)`.
- **`PromotionService`** — after a completion, checks whether all active `Lesson`s in the student's `CurrentRankId` are complete; if so, closes the current `StudentRankProgress` row, opens the next, advances `Student.CurrentRankId`, and awards the `RankBadge` via a new `StudentBadge`. At the final rank, sets `Student.Status = Graduated` instead of advancing further.
- **`LessonLibraryService`** (FR-006) — read side of the lesson library. `GetLibraryAsync()` returns ranks (`Rank.Order`) with their active lessons (`Lesson.Order`), tags and files; `OpenFileAsync(lessonFileId)` reads a file of an active lesson through `IBlobStorage.ReadAsync`. Teacher, Approver, Admin, Student and Parent only, checked in the service and by the `RequireLessonLibrary` policy (plus the MFA requirement). Served by `GET /lessons/files/{id}` (by `LessonFile.Id`, never a blob key): PDF and images `inline`, everything else `attachment`, always `nosniff`.
- **`CertificateService`** — generates a PDF via QuestPDF from a template, uploads it via `IBlobStorage` (local disk on the VPS — `LocalDiskBlobStorage`), writes a `Certificate` row.
- **`ConsentExpiryJob`** (`Vlms.Jobs`, invoked daily by a systemd timer on the self-hosted VPS — `adr/0003-scheduled-jobs-webjobs.md` as amended by `adr/0005-hosting-pivot-self-hosted-vps-postgresql.md`) — daily sweep: flags consents/DBS checks expiring within a configurable window and expired ones, triggers `NotificationService` emails, escalates to Admin/Safeguarding Officer. Also runs the at-risk/disengaged student flagging: no lesson completion within 8 weeks (`functional.md`), and surfaces the "records due for deletion" report (`data-design.md` — deletion enforcement).
- **`NotificationService`** — wraps Microsoft Graph `sendMail` (`GraphEmailSender`, app-only, scoped to the `noreply@varangians.co.uk` mailbox — `adr/0005` amendment; originally Azure Communication Services Email, then SMTP/MailKit) for: lesson completion/promotion confirmations to parents, consent-expiry reminders, at-risk flags to Admin. **Failure handling (design-review addition):** a failed send for a safeguarding-critical notification (expired consent, expired DBS) is retried with backoff and, if still failing, logged as an escalation-visible failure to Admin — a silent failure here must not be possible, since it's the mechanism that surfaces a safeguarding lapse. Non-critical notifications (e.g. routine completion confirmations) log failure without escalation.
- **`GuardianNotificationService`** (BR-005) — builds the parent-facing emails and sends them through `NotificationService`. **Recipients:** guardians linked to the student by `StudentGuardianLink` whose account holds `Parent` (Admin-approved, FR-004) and has not left; never `ParentGuardian.ContactInfo`. **Completion/promotion:** called by `CompletionService.MarkCompleteAsync` after the completion, promotion and certificate are saved; one email per completion plus one on promotion or programme completion; Standard priority; never throws, so a mail failure cannot fail or undo the completion. **Consent reminders:** called by `Vlms.Jobs` after the daily sweep; read from the consent records directly, for Active students who have not left, to linked parents who have not left (adr/0008 answer 3): a renewal email when the consent in force expires in exactly 30, 14, 7 or 1 days (31 August under the church-year rule, `ConsentYear`) with no later-expiring approved consent and no Pending form; a weekly email (every Monday) while the child has no consent in force or the latest form was rejected and awaits resubmission; plus one safeguarding-critical notice the day after the last approved consent ends (on a Monday it replaces the weekly email, never doubles it). Links go to `/parent/consent`. No sent-reminder state is stored, so a missed daily run skips that day's reminder; each student is processed in its own try/catch. **Content:** student name, lesson title, rank name, consent expiry date, and a `/parent/dashboard` link when `App:PublicBaseUrl` is set; nothing from `DbsCheck` or `ConsentSensitiveDetails`.
