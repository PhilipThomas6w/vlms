# 0004 - Sensitive data access control: entity split + EF Core query filters + read audit log

## Status

Accepted (revised after design review: pass 2 corrected the masking mechanism itself, pass 3 corrected the audit-write mechanism; later revised again at implementation time — pass 5 re-targeted the tamper-protection DENY from a dedicated `VlmsAppRole` to `public` to close a forgettable-provisioning gap; pass 6 ported §4 to PostgreSQL for `adr/0005-hosting-pivot-self-hosted-vps-postgresql.md` and found the port is *not* strength-equivalent to the SQL Server original — see Context, Decision §4, and Alternatives considered; pass 7 added an MFA precondition to the `DbsCheck`/`ConsentSensitiveDetails` query filters themselves, alongside the identity-provider swap in `STATE.md`'s "Identity" item — see Decision §5)

**Implemented (pass 6):** `adr/0005-hosting-pivot-self-hosted-vps-postgresql.md` moved the database engine from Azure SQL Database to self-hosted PostgreSQL. The access-control *design* here — EF Core global query filters on `DbsCheck`/`ConsentSensitiveDetails`, the `IMaterializationInterceptor` read-audit trail — is provider-independent and did not change; both are confirmed still fully covered by the existing SQLite-in-memory test suite (166/166 tests passing, unchanged test logic — see `openwiki/testing.md`'s "Test-provider strategy" section for why that's expected, not just hoped). §4's tamper-protection DDL was ported to `REVOKE UPDATE, DELETE ON sensitive_data_access_logs FROM PUBLIC` (one migration, `RevokeUpdateDeleteOnSensitiveDataAccessLog`, replacing the two deleted SQL-Server-specific migrations) — but this is **not** the "same structural guarantee, ported not redesigned" this ADR originally expected when pass 6 was scoped; see Decision §4 for what was actually verified and why.

## Context

VLMS stores special-category and children's personal data directly (`DbsCheck`, and originally three sensitive fields on `ConsentRecord`) with a confirmed, role-specific access model: `DbsCheck` is restricted entirely to Admin/Safeguarding Officer; the sensitive consent fields are masked from Teacher and Approver, who nonetheless still need `ConsentRecord.Status`/`ExpiryDate` to enforce the consent-blocks-lesson-completion rule (FR-003).

A design review raised three issues, the first of which invalidated the original mechanism:

1. **The original decision specified EF Core global query filters to mask individual `ConsentRecord` columns.** This is not possible: a global query filter is a row-inclusion predicate (`HasQueryFilter`) — it can only include or exclude an entire row, not redact specific columns within a row that a role otherwise legitimately needs (Teacher needs `Status`/`ExpiryDate` from the same row the sensitive fields lived on). The mechanism as originally specified could not deliver the masking it claimed to. **Fixed at pass 2** by splitting the entity (see Decision §1–2).
2. If masking/restriction is instead implemented as an opt-in per-call convention, one missed query/report call site leaks sensitive data.
3. The original design logged who *created/approved* a safeguarding record but nothing logged who subsequently *read* one.
4. **Pass 3 found the pass-2 fix for issue 3 was itself under-specified:** a `DbCommandInterceptor` operates on raw ADO.NET commands/`CommandText` and a forward-only `DbDataReader` — it has no direct access to EF's typed entity model, so "detects commands against these two tables and writes the audit row" glossed over how a specific `EntityId` gets extracted (SQL text-matching is fragile against joins/aliasing; reading the `DbDataReader` inside the interceptor risks exhausting it before EF materializes from it). It would also miss cache-hit-driven correctness questions the alternative mechanism below doesn't have. **Fixed at pass 3** (see Decision §3).

## Decision

1. **Split `ConsentRecord` into two entities** (`design/data-design.md`): `ConsentRecord` (status, expiry, non-sensitive consent flags — readable by Teacher/Approver) and `ConsentSensitiveDetails` (medical, dietary/SEN, emergency contact — 1:1 with `ConsentRecord`). This turns the masking requirement into the same *whole-entity* restriction pattern already correctly used for `DbsCheck`, which a query filter can actually enforce.
2. Enforce whole-entity restriction on `DbsCheck` and `ConsentSensitiveDetails` structurally via **EF Core global query filters** on the `DbContext`, keyed by the current caller's role. Bypassing requires an explicit, greppable `IgnoreQueryFilters()` call — a reviewable act, not an accident.
3. Add a `SensitiveDataAccessLog` table and write an entry on every read of `DbsCheck` or `ConsentSensitiveDetails` (who, what, when, view vs export). **Write mechanism (corrected at pass 3):** an [`IMaterializationInterceptor`](https://learn.microsoft.com/ef/core/logging-events-diagnostics/interceptors) registered on the `DbContext`. Its `InitializedInstance` hook fires once per entity instance EF materializes from a query result, giving direct typed access to the entity (`entity is DbsCheck dbs → log dbs.Id`) — no SQL text-matching, no manual `DbDataReader` handling, and it fires correctly per row even across EF's compiled-query cache (unlike `IQueryExpressionInterceptor`, which only fires at query-plan compilation and would silently miss a second call with the same query shape but different parameters — a real risk for an audit-every-read requirement). Because `IMaterializationInterceptor` is registered as a singleton shared across `DbContext` instances, the current-user context is resolved per-call via `materializationData.Context.GetService<T>()`, not cached on the interceptor.
4. `SensitiveDataAccessLog` has `UPDATE`/`DELETE` denied at the database permission level (not just an application-level "append-only" convention), and is retained 6 years regardless of the referenced record's own retention. **Implemented for SQL Server, then revised (pass 5) to close a forgettable-provisioning gap, then ported to PostgreSQL (pass 6) with a verified, disclosed strength gap.**

   **Pass 4/5 (SQL Server, historical — the mechanism below no longer runs; kept as the record of what was built and why, per this ADR's own convention).** The original `DenyUpdateDeleteOnSensitiveDataAccessLogs` migration created a dedicated database role, `VlmsAppRole`, and denied `UPDATE`/`DELETE` to that role — a later checker review found this left the DENY inert until a deployer remembered to add the production principal to the role. `SupersedeVlmsAppRoleWithPublicDenyOnSensitiveDataAccessLogs` re-targeted the DENY to SQL Server's `public` database role instead: every database user belongs to `public` and cannot be removed from it ([Database-Level Roles](https://learn.microsoft.com/en-us/sql/relational-databases/security/authentication-access/database-level-roles)), and `DENY` overrides all grants except for object owners and `sysadmin` ([DENY (Transact-SQL)](https://learn.microsoft.com/en-us/sql/t-sql/statements/deny-transact-sql)) — so the only principals that could still mutate the log were `dbo` and `sysadmin`, an override that held regardless of any other grant a principal held.

   **Pass 6 (PostgreSQL, current — adr/0005-hosting-pivot-self-hosted-vps-postgresql.md).** Both SQL Server migrations were deleted (no live database anywhere held applied migration state — confirmed from STATE.md before deleting, not assumed) and replaced with one, `RevokeUpdateDeleteOnSensitiveDataAccessLog`: `REVOKE UPDATE, DELETE ON sensitive_data_access_logs FROM PUBLIC;`. **This is not the same structural guarantee "ported not redesigned" that adr/0005 anticipated** — checked against current PostgreSQL documentation rather than assumed the SQL Server mental model carries over, per CLAUDE.md "verify, don't invent", and the gap is disclosed here rather than papered over:
      - PostgreSQL's privilege model has **no override concept**. `REVOKE ... FROM PUBLIC` removes only the privilege a role held *via* `PUBLIC`; a role holding `UPDATE`/`DELETE` some other way — an explicit direct `GRANT`, or by owning the table — is completely unaffected ("revoking SELECT privilege from PUBLIC does not necessarily mean that all roles have lost SELECT privilege on the object: those who have it granted directly ... will still have it" — [REVOKE](https://www.postgresql.org/docs/current/sql-revoke.html)). It is also not persistent the way `DENY` is: a later `GRANT ... TO PUBLIC` would silently restore what this `REVOKE` removed, with nothing re-blocking it.
      - PostgreSQL grants **no default privileges to `PUBLIC` on tables at all** ("No privileges are granted to PUBLIC by default on tables ..." — [Privileges](https://www.postgresql.org/docs/current/ddl-priv.html)), unlike SQL Server. On a freshly created table this `REVOKE` has nothing to revoke; it is defensive against a future accidental `GRANT ... TO PUBLIC`, not an active restriction from day one.
      - Consequently, **who can still `UPDATE`/`DELETE` the log is a strictly larger set than "the owner and a superuser"** (the analogy originally expected, mirroring SQL Server's `dbo`/`sysadmin`) — it is *any* role ever explicitly granted `UPDATE`/`DELETE` directly, or that owns the table. The residual, load-bearing control is therefore entirely operational, more so than it was under SQL Server's DENY: the app's connecting role must never own this table and must never be granted `UPDATE`/`DELETE` on it directly (only `SELECT`/`INSERT`, which `SensitiveDataAuditInterceptor`'s writes need) — `governance/raid.md` D-004, generalised for PostgreSQL.
      - A true `DENY`-equivalent **does** exist in PostgreSQL — Row-Level Security (`ALTER TABLE ... FORCE ROW LEVEL SECURITY` plus `CREATE POLICY ... FOR UPDATE USING (false)` / `FOR DELETE USING (false)`, which blocks even the table owner, with only a superuser/`BYPASSRLS` role exempt — verified against [Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)) — but was **deliberately not built in pass 6**: enabling row security requires an explicit policy for every command that must keep working or that command is default-denied too, and getting that wrong risked silently blocking the audit interceptor's own `INSERT` path inside what was scoped as a same-provider port, not a mechanism redesign. Tracked as a new, separate, higher-scrutiny follow-up (`STATE.md` Next).

   `INSERT` is deliberately not revoked (the `SensitiveDataAuditInterceptor`'s own writes must keep working), and `TRUNCATE` is not named anywhere in this ADR or `governance/security-compliance.md`, so it isn't revoked either — unchanged from the SQL Server version. This is raw PostgreSQL SQL and is never applied against the SQLite in-memory provider the test suite uses (tests build schema via `Database.EnsureCreated()`, never `Database.Migrate()`); verified via tests that generate the real migration SQL through EF Core's `IMigrator.GenerateScript()` against an Npgsql-configured context and assert the exact `REVOKE` statement, migration ordering, and that `INSERT`/`TRUNCATE` are untouched (`tests/Vlms.Tests/Infrastructure/MigrationsTests.cs`) — structurally correct, not yet exercised against a live PostgreSQL server, the same status other provider-dependent code in this repo carries until a live resource exists; it proves the literal statement is present, not that it achieves `DENY`'s override semantics, which it verifiably doesn't (above). The 6-year retention itself (a purge/retention job) is a separate, not-yet-built concern — out of scope for this tamper-protection item.

5. **MFA-gated roles (pass 7 — `STATE.md` "Identity" item, item 4 of that item's own scope).** When the identity provider was swapped from Microsoft Entra External ID to self-rolled ASP.NET Core Identity with built-in TOTP MFA, the `HasQueryFilter` predicates on `DbsCheck` and `ConsentSensitiveDetails` gained a second conjunct:

   ```csharp
   e.HasQueryFilter(x =>
       (_currentUser.HasRole(Role.Admin) || _currentUser.HasRole(Role.SafeguardingOfficer))
       && _currentUser.HasMfaEnabled);
   ```

   **(a) Why the query filter, not just the pages.** The same identity-swap item also added a new `MfaRequirement`/`MfaRequirementHandler` that rides every `AddAuthorization` policy in `Program.cs` — including the `/safeguarding/*` pages that are the *only intended* UI path to these two entities. That page-level gate is necessary but not sufficient: `VlmsDbContext` is also consumed directly by other code that isn't a gated page (`ConsentExpiryJob`'s daily sweep, `ProgressReportingService`, any future reporting/export feature), and this ADR's own governing principle (Decision §2: "restriction must be structural, not a per-call convention a future caller might forget") applies exactly as much to "did this caller pass the MFA check" as it already applies to "does this caller hold the right role" — an Admin/SafeguardingOfficer who has not yet enrolled MFA is denied the safeguarding pages by `MfaRequirementHandler`, but without this conjunct they could still read `DbsCheck`/`ConsentSensitiveDetails` in full through any other code path that queries the `DbContext` directly, since nothing at the data layer would stop them. Putting the check in the query filter closes that gap the same way the filter itself already closes the analogous "some other page/service forgets to check the role" gap — one structural mechanism, not two independently-maintained ones (a page check and a data check) that could drift apart.

   **(b) Why `SystemCurrentUserContext.HasMfaEnabled` is hardcoded `true`.** `ConsentExpiryJob` (the one caller of `SystemCurrentUserContext`, `Vlms.Jobs`) is a scheduled background process with no signed-in human operator — TOTP MFA is a control on *interactive sign-in by a person*, and there is no session, credential, or Identity row for a system principal to have "enabled" it against. Requiring `HasMfaEnabled` to be `false` (or unresolvable) for a non-human caller would silently break the daily consent/DBS expiry sweep — the one place this codebase already depends on reading `DbsCheck` through the normal filtered/audited path (never `IgnoreQueryFilters()`) — for a reason that has nothing to do with what the MFA control actually protects against (a compromised or shared human credential). `SystemCurrentUserContext.HasRole` is already narrowly scoped to exactly `Role.Admin`/`Role.SafeguardingOfficer` (precisely what the filter checks), not a general bypass; hardcoding `HasMfaEnabled = true` is the same narrow-scoping discipline applied to the new conjunct, not a loophole — it does not let `SystemCurrentUserContext` read anything a correctly-configured human Admin/SafeguardingOfficer couldn't also read.

   Enforced globally for Admin/SafeguardingOfficer specifically (both at the query filter and via `MfaRequirement` on every policy); offered, never required, to every other role — see `openwiki/authentication-authorization.md`'s MFA section for the full scope decision and `openwiki/access-control.md`'s mechanism section for the current query-filter text. Tested in `tests/Vlms.Tests/Infrastructure/SensitiveDataAccessControlTests.cs`'s "MFA-gated roles" cases (Admin/SafeguardingOfficer denied without MFA; SafeguardingOfficer allowed with it, confirming the denial is about MFA specifically and not a role regression).

## Alternatives considered

- **Per-column masking via a query filter** (the original decision) — rejected: technically impossible for the reason above; kept here as a record of what was wrong, not as a live option.
- **Per-call data-access-layer policy checks** — rejected: correct in principle, but relies on every future query author remembering to apply it; not structural.
- **Database-level column encryption** (e.g. Always Encrypted) — rejected for v1: real operational complexity (key management, limited queryability) disproportionate to a solo-maintained, tens-of-users system; the entity-split + query-filter approach gives equivalent access control for the actual threat model here (accidental over-exposure within the application, not a compromised database administrator).
- **A mandatory repository wrapper method for the audit log write** — rejected: a wrapper is opt-in by construction (a new query path could bypass it).
- **`DbCommandInterceptor`** (the pass-2 decision) — rejected at pass 3: operates on raw SQL/`CommandText` and a forward-only `DbDataReader`, with no direct route to a typed `EntityId` without fragile text-matching or reader-handling that risks conflicting with EF's own materialization. Kept here as a record of what was under-specified, not as a live option.
- **`IQueryExpressionInterceptor`** — rejected: fires once per query-plan compilation, not per execution, so a second call with the same query shape but a different parameter (e.g. a different student's `ConsentSensitiveDetails`) would not re-trigger it under EF's compiled-query cache — silently under-recording exactly the reads this control exists to catch.
- **A dedicated `VlmsAppRole` for the tamper-protection DENY** (the pass-4 decision) — rejected at pass 5: an opt-in role starts with zero members, so the `DENY UPDATE`/`DELETE` on `SensitiveDataAccessLogs` was inert until a deployer remembered to add the production principal — a control that could silently protect nothing despite the migration running cleanly. Scoping a broad tamper-protection restriction to a role you opt into inverts the intent of the control. Replaced by `DENY ... TO public` (see Decision §4), which applies to every principal automatically. Kept here as a record of what was under-provisioned, not as a live option. Superseded entirely at pass 6 by the PostgreSQL port below (SQL Server's DENY no longer runs at all).
- **Row-Level Security for the PostgreSQL tamper protection** (pass 6) — considered as the mechanism that would actually deliver `DENY`'s override-every-grant guarantee (see Decision §4), and **deferred, not rejected**: it needs an explicit policy for every command that must keep working (`SELECT`/`INSERT`) or that command is default-denied too the moment row security is enabled, and a mistake there would silently break the audit interceptor's own `INSERT` path — too much new risk to fold into a same-provider migration port. Tracked as a separate, deliberately higher-scrutiny follow-up (`STATE.md` Next) rather than attempted in pass 6.
- **MFA enforced only at the page/policy layer** (pass 7 — the `MfaRequirement` policy alone, with no query-filter conjunct) — rejected: this ADR's own governing principle is that whole-entity restriction must be structural at the data layer, not something every caller/page has to remember (Decision §2); a page-only gate leaves any non-page code path (a scheduled job, a future report/export) able to read `DbsCheck`/`ConsentSensitiveDetails` for an MFA-less Admin/SafeguardingOfficer with nothing to stop it. See Decision §5(a).

## Consequences

- All EF Core queries against `DbsCheck`/`ConsentSensitiveDetails` go through the shared `DbContext` with filters and the audit interceptor applied; any new reporting/export feature is safe and logged by default.
- Any code needing both consent status and sensitive details (there is currently none identified) must join `ConsentRecord` and `ConsentSensitiveDetails` explicitly and will be denied the latter unless the caller's role permits it.
- The read-audit log adds write volume proportional to how often sensitive data is viewed — negligible at tens-of-users scale — and its own 6-year retention is independent of the referenced record's retention.
- OWASP ASVS 5.0's access-control and logging chapters should be checked against this mechanism at build/test time (`quality/test-plan.md` TC-007/TC-008/TC-011), not just assumed satisfied by this ADR.
