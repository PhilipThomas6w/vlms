# OWASP ASVS 5.0 access-control review checklist

Gated by `build/check-access-control.ps1` as part of `build/verify.ps1`'s full run (skipped by
`-Fast`). This file is not decorative: the script hashes the source files listed under "Reviewed
scope" below and compares that hash to the `Reviewed-hash` line at the bottom of this file. If they
don't match — because any of those files changed since the last time a human worked through this
checklist — the stage fails until someone re-reviews it and records the new hash (run
`pwsh -File build/check-access-control.ps1 -PrintHash`).

**Chapter correction:** STATE.md's item wording named this "ASVS 5.0 V1", following the ASVS 4.0.3
numbering where access control was V4. ASVS 5.0 renumbered its chapters; checked against OWASP's
own 5.0.0 table of contents rather than assumed — in 5.0, **V1 is "Encoding and Sanitization"** and
**access control/authorization is V8**. This checklist targets V8, with supporting items from V14
(Data Protection — the whole-entity restriction mechanism) and V16 (Security Logging — the
read-audit trail), matching `adr/0004-sensitive-data-access-control.md`.

## What's automated (build/check-access-control.ps1), not repeated here

- Every routable Razor page carries `@attribute [Authorize(...)]`, except the named allow-list
  (`Home.razor` — gated per-link via `<AuthorizeView>`, not page-level; `Error.razor`/`NotFound.razor`
  — framework pages with nothing sensitive).
- No `.IgnoreQueryFilters()` call exists anywhere in `src/` (adr/0004 decision #2: bypassing the
  `DbsCheck`/`ConsentSensitiveDetails` query filters must be a reviewable, greppable act, and
  currently there are zero such call sites).
- Raw SQL (`SqlQuery*`, `FromSql*`, `ExecuteSql*`) appears only in the three files `adr/0010-chapters.md`
  sanctions (`VlmsDbContext.cs`, `Chapters/NationalTotalsService.cs`, `Guardianship/GuardianInviteService.cs`),
  and `ChapterScopeOverride.EnterForVerifiedInvite` is called only by `GuardianInviteService` (24/10/2026).
- `SensitiveDataAccessControlTests.cs`, `ConsentRecordServiceTests.cs`, `DbsCheckServiceTests.cs`,
  `GuardianLinkServiceTests.cs` (test-plan.md TC-007/008/011/012) still exist with at least as many
  test methods as when this stage was written.

Those three are re-verified every full run. What follows is the part that genuinely needs a human:
whether the *design* is still sound, not just whether the code matches last time's design.

**Identity item update (2026-07-20):** STATE.md's "Identity" item replaced Microsoft Entra External
ID with self-rolled ASP.NET Core Identity (TOTP MFA) and the Microsoft Graph guardian-invitation
mechanism with a self-rolled signed/single-use/expiring invite link. The allow-list above now also
names every sign-in/account-creation page this introduced (`Login.razor`, `Register.razor`,
`LoginWith2fa.razor`, `LoginWithRecoveryCode.razor`, `AcceptInvite.razor`) — each is unauthenticated
by necessity, and each was checked (not merely allow-listed) to confirm it takes no sensitive data

are deliberately NOT on the allow-list — they carry a plain `[Authorize]` (any signed-in user, not a
`RequireX` policy — enforcing MFA enrolment itself behind an MFA requirement would be a lockout
catch-22, see `TwoFactorAuthentication.razor`'s own doc comment), which the automated check already
accepts as satisfying "every routable page has `[Authorize]`".

**Password reset + Identity hardening update (2026-10-12):** the allow-list also names
`ForgotPassword.razor`, `ResetPassword.razor`, `ConfirmEmail.razor` and `ResendEmailConfirmation.razor`
— reached by someone who can't sign in yet. `AccountEmailService.cs` and `VlmsIdentityPolicy.cs` are

## V8 Authorization — manual review items

- [ ] Every `Role` enum value used by a policy in `Program.cs`'s `AddAuthorization` block
      (`Admin`, `Teacher`, `Approver`, `Parent`, `Student`, `SafeguardingOfficer` — one
      `Require{Role}` policy each, per `RoleRequirement`/`RoleAuthorizationHandler`) still matches
      `docs/design/low-level-design.md`'s "Authorization model" section and
      `docs/governance/security-compliance.md`'s "Access control by role" section. No new role has
      been added to the codebase without also being added to those docs.
- [ ] The **Approver** role still carries no path to `ConsentRecord`, `ConsentSensitiveDetails`, or
      `DbsCheck` — confirmed by reading `Program.cs`'s policy list (`RequireApprover` is used only
      by `Curriculum/ApproverProposals.razor`) and by `ConsentRecordService`/`DbsCheckService`'s own
      in-service role checks (`Role.Admin`/`Role.SafeguardingOfficer` only — never `Role.Approver`),
      `ParentConsentService` (`Role.Parent` only) and `StudentConsentViewService` (`Role.Teacher`/
      `Role.Admin`/`Role.SafeguardingOfficer` only). The `ConsentSensitiveDetails` query filter has
      no Approver arm (adr/0006); a user holding only Approver reads no row
      (`SensitiveDataAccessControlTests.Parent_And_Approver_CannotRead_DbsCheck`,
      `ParentConsentServiceTests.ApproverOnlyUser_ReadsNoSensitiveDetailsAtAll`).
      This is the CLAUDE.md hard constraint ("the Approver role is curriculum-only, never conflated
      with safeguarding/consent sign-off") — re-check it by name at every review, not by assumption.
- [ ] Resource-based checks are still correctly scoped: `ParentStudentAccessHandler` (via the shared
      `ParentGuardianLinkage` helper) only grants a Parent access to `Student`s reachable through
      their own `StudentGuardianLink` rows; `StudentSelfAccessHandler` only grants a Student their
      own record; `TeacherStudentAccessHandler` intentionally grants **all** students to every
      Teacher (confirmed design decision, low-level-design.md — teachers cover for each other, no
      `AssignedTeacherUserId` scoping). Confirm no new resource type has been added that needs an
      equivalent handler but doesn't have one.
- [ ] `StudentGuardianLink` rows are still only ever created by `GuardianLinkService`/
      `StudentRegistrationService`, both role-checked to Admin/Teacher inside the service itself
      (defense in depth, not just page-level `[Authorize]`) — grep for any other code path that
      calls `.Add(...)` on `StudentGuardianLink`s and confirm there isn't one.
- [ ] Every new service added since the last review that touches `DbsCheck`,
      `ConsentSensitiveDetails`, `ConsentRecord`, or `StudentGuardianLink` performs its own
      in-service role check (the established defense-in-depth pattern — see
      `LessonProposalService`/`GuardianLinkService`/`ConsentRecordService`/`DbsCheckService`), not
      solely a page-level `[Authorize]` policy that a future non-page caller (a job, an API) could
      bypass. Checked for this review's two new services: `GuardianInviteService.IssueAsync` checks
      Admin-or-Teacher itself (`RequireAdminOrTeacher`, mirroring `GuardianLinkService`, its only
      caller); `AppUserProvisioningService.CreateAsync` deliberately has **no** role check — it never
      touches any of the four listed entities, and is reachable by design from an unauthenticated
      caller (`Register.razor`, the guardian invite-accept flow) — a new `AppUser` always gets zero
      `UserRole` rows (deny-by-default), so this is not a gap.
- [ ] **Parent consent form and teacher consent view (functional.md FR-015,
      adr/0006-parent-consent-and-teacher-read-access.md, 22/10/2026).** Writes to
      `ConsentRecord`/`ConsentSensitiveDetails` happen only in `ConsentRecordService.RecordAsync`
      (Admin/SafeguardingOfficer, paper form) and `ParentConsentService.SubmitAsync` (Parent). A query
      filter does not govern writes, so `SubmitAsync` itself requires `Role.Parent`, a resolved
      `UserId`, `AppUser.HasLeft == false`, and a `StudentGuardianLink` from a `ParentGuardian` whose
      `AppUserId` is the caller to the target student — tested by
      `ParentOfAnotherChild_CannotSubmit_ForThatChild_AndNothingIsCreated` and
      `ParentWhoHasLeft_CannotReadOrSubmit`. A submission is always a new Pending row: no parent
      path updates or deletes an existing `ConsentRecord`/`ConsentSensitiveDetails` row. Only
      `ConsentRecordService.DecideAsync` (Admin/SafeguardingOfficer, Pending only, comments required
      to reject) changes a record's status, and only an approval writes `Student.Name`/
      `Student.DateOfBirth` (FR-013; never status, rank or assigned teacher). Teachers have no write
      method at all (`StudentConsentViewService` is read-only; `Teacher_CannotWrite_ConsentOrDecide`).
      Pages: `/parent/consent` (`RequireParent`), `/students/consent` and `/students/{id}/consent`
      (`RequireTeacher`), `/safeguarding/consent` (`RequireAdminOrSafeguardingOfficer`), each with
      `MfaRequirement` via its policy.
- [ ] **MFA enforcement (STATE.md "Identity" item 4) is wired at both layers, not just one:** every
      policy in `Program.cs`'s `AddAuthorization` block (`Require{Role}` × 6, `StudentAccess`,
      `RequireAdminOrTeacher`, `RequireAdminOrSafeguardingOfficer`) also carries an `MfaRequirement`,
      handled by `MfaRequirementHandler` — which succeeds unless the caller holds `Role.Admin`/
      `Role.SafeguardingOfficer`/`Role.Teacher` (Teacher added 22/10/2026, adr/0006 amendment)
      without `ICurrentUserContext.HasMfaEnabled`. Confirm no future policy
      is added to `Program.cs` without also adding `new MfaRequirement()` — a policy that forgets it
      would let an Admin/SafeguardingOfficer/Teacher without MFA reach that specific page even though every
      other page in the app blocks them, silently narrowing the "globally enforced" design intent
      (`MfaRequirement`'s own doc comment) down to "enforced on most pages".

- [ ] **Role assignment and first-Admin bootstrap (STATE.md "Admin role assignment + first-Admin
      bootstrap", 2026-10-11):** `RoleAssignmentService` is still the only code that writes or
      deletes `UserRole` rows from `Vlms.Web`, is still Admin-only inside the service (every method,
      including `ListUsersAsync`), still refuses to revoke the last Admin, and still refuses grants
      to a leaver. `ApproveGuardianAsParentAsync` still grants only `Parent`, only to an account that
      consumed a guardian invite (a self-registered account cannot be one-click approved), and goes
      through `GrantAsync`'s own guards. `FirstAdminBootstrapService` is still wired only into `Vlms.Jobs`
      (`bootstrap-admin`), never `Vlms.Web` (`FirstAdminBootstrapWiringTests`), and still refuses
      to run once any Admin exists. `Administration/UserRoles.razor` is still gated by
      `RequireAdmin` (which carries `MfaRequirement`). The bootstrap also still refuses an account
      whose email isn't confirmed, so a squatter who registered first under the operator's address
      can't be the one promoted.

- [ ] **Account recovery and email confirmation (STATE.md "Password reset + Identity hardening",
      2026-10-12):** `VlmsIdentityPolicy` still requires a confirmed email to sign in, and only the
      guardian-invite path creates an account pre-confirmed (the invite was emailed to that
      address). `AccountEmailService` still sends a reset link only to a confirmed account, gives
      the same response for unknown emails, and relies on Identity's single-use codes (security
      stamp rotation) with `VlmsIdentityPolicy.EmailTokenLifespan` expiry. A reset grants no role
      and bypasses no MFA: a user with TOTP enabled still needs it at the next sign-in.

- [ ] **Student sign-ins (FR-011, `adr/0007-student-sign-in-accounts.md`, 22/10/2026):**
      `Identity/StudentAccountService` is still the only code that grants `Role.Student` and sets
      `Student.AppUserId`; `RoleAssignmentService.GrantAsync` still refuses `Student` and refuses
      any role to an account a `Student` row points at. Creating a sign-in still requires the
      `Parent` role, a `StudentGuardianLink` to that student (`ParentGuardianLinkage`) and
      `AppUser.HasLeft` false, all checked in the service; a second sign-in for the same student is
      refused, including under a race (conditional `WHERE app_user_id IS NULL` update inside the
      creating transaction). Reset still requires that linked parent or an Admin with MFA, and
      still refuses an account with an email address, so it can never reach an adult account.
      `VlmsUserConfirmation` still applies the confirmed-email rule to every account with an email
      and admits an emailless account only when a `Student` row names it. Student usernames still
      can't contain `@` (`StudentUsername`) and adult accounts still must (`AppUserProvisioningService.CreateAsync`),
      so the two can't collide. `/student` (`RequireStudent`) still takes no id and resolves the
      caller's own record (`StudentPageService`); `/parent/student-sign-ins` (`RequireParent`) and
      `/administration/student-sign-ins` (`RequireAdmin`) are still policy-gated. Students still
      have no MFA requirement (decision in `MfaRequirementHandler`), and the login rate limit still
      covers their sign-ins (same `/Account/Login` page).
      Sign-in rules (Philip, 22/10/2026, adr/0007 decisions 9–13): `VlmsPasswordValidator` still
      sends every account with an email to Identity's own base validator with the unchanged
      global options, and requires only 8+ characters of an emailless (student) account; it is
      still the only registered `IPasswordValidator`. Disable and restore
      (`StudentAccountService.DisableSignInAsync`/`RestoreSignInAsync`) still require an Admin with
      MFA, set `VlmsIdentityUser.SignInDisabled` and rotate the security stamp in one update;
      `VlmsUserConfirmation` still refuses a disabled account; a reset still never touches the
      flag. A parent's or Admin's reset still clears lockout only after the reset succeeds.
      `VlmsSignInManager` still forces a persistent, 90-day sliding cookie only for emailless
      accounts, and `Program.cs` still sets `SecurityStampValidatorOptions.ValidationInterval`, so
      a long-lived cookie is still rechecked against the stamp.

- [ ] **Role changes take effect immediately (FR-016, 22/10/2026):**
      `Security/IdentityCurrentUserContext` still re-reads `UserId`, `HasRole` and `HasMfaEnabled`
      from the database on every call, with no `Lazy`, field cache or other per-scope memo (a
      Blazor Server circuit's DI scope lasts as long as the circuit, so any scope-level cache
      reintroduces the defect). It still never takes a DI-resolved `VlmsDbContext` (circular
      dependency) and still resolves the principal through `AuthenticationStatePrincipalResolver`.
      `RoleAssignmentService.GrantAsync`/`RevokeAsync` (and so `ApproveGuardianAsParentAsync`) and
      `LeavingService.MarkStaffLeftAsync` still call `SecurityStamps.RotateAsync`
      (`UserManager.UpdateSecurityStampAsync`) inside the same transaction as the change. The
      cookie's `SecurityStampValidatorOptions.ValidationInterval` (Program.cs) and
      `IdentityRevalidatingAuthenticationStateProvider.RevalidationInterval` are still both
      `VlmsIdentityPolicy.SecurityStampValidationInterval` (1 minute). Multi-role users still get the
      union of their roles' permissions and nothing more (`RoleChangeTests`); no permission layer
      exists beyond the fixed per-role policies, filters and in-service checks.

## V14 Data Protection — manual review items

- [ ] The `HasQueryFilter` predicate on `DbsCheck` in `VlmsDbContext.OnModelCreating` still reads
      exactly `(_currentUser.HasRole(Role.Admin) || _currentUser.HasRole(Role.SafeguardingOfficer)) &&
      _currentUser.HasMfaEnabled` (adr/0004 §"MFA-gated roles" pass 7: the `&& HasMfaEnabled`
      conjunct closes the gap where an Admin/SafeguardingOfficer without MFA could still read these
      entities through any code path querying `VlmsDbContext` directly). **Amended 22/10/2026
      (adr/0006, FR-015):** the predicate on `ConsentSensitiveDetails` is now that same Admin/
      SafeguardingOfficer-with-MFA arm, OR `_currentUser.HasRole(Role.Teacher) &&
      _currentUser.HasMfaEnabled` (MFA conjunct added 22/10/2026, adr/0006 amendment), OR
      `_currentUser.HasRole(Role.Parent) && _currentUser.UserId != null &&
      StudentGuardianLinks.Any(link => link.StudentId == x.ConsentRecord!.StudentId &&
      link.ParentGuardian!.AppUserId == _currentUser.UserId && !link.ParentGuardian.AppUser!.HasLeft)`.
      Re-check by reading the code that: the Parent arm is scoped by the link to the row's own
      student (not "any link"); the `UserId != null` and `!HasLeft` conjuncts are both still present
      (each alone excludes account-less guardians for a Parent caller with no resolved id — found by
      break-testing, see the 22/10/2026 row); there is still no Approver/Student arm; the Teacher arm still
      carries `&& _currentUser.HasMfaEnabled` (closes adr/0006 risk 1); the Parent arm is deliberately
      not MFA-gated (MFA offered to Parents, not required — Philip has not asked for it). No further role is added to
      either filter without an explicit, documented decision.
- [ ] `SystemCurrentUserContext` (used only by the `Vlms.Jobs` systemd-timer-invoked console host) still grants exactly
      `Role.Admin`/`Role.SafeguardingOfficer` and nothing broader, and its `HasMfaEnabled` is hardcoded
      `true` (documented in its own doc comment: MFA enforcement gates *interactive sign-in* by a
      human, which this trusted, narrowly-scoped system principal is not) — it is a narrow, named
      exception to "no code bypasses the filter", not a general bypass.
- [ ] `SensitiveDataAccessLog`'s database-level tamper protection — now `REVOKE UPDATE, DELETE ON
      sensitive_data_access_logs FROM PUBLIC` on PostgreSQL (adr/0004 §4 pass 6,
      adr/0005-hosting-pivot-self-hosted-vps-postgresql.md; was SQL Server `DENY ... TO public`).
      The `REVOKE` alone was verified weaker than the SQL Server original, not equivalent; the
      Row-Level Security layer in adr/0004 §6 (pass 8) closes that gap, and is a true DENY-equivalent
      only for the roles this deployment creates (a genuine superuser or `BYPASSRLS` session still
      bypasses it — adr/0004 §6(e)). See adr/0004 §4 and §6 and openwiki/access-control.md. Confirm the
      residual, now-more-load-bearing requirement is still tracked (`governance/raid.md` D-004: the
      app's connecting role must never be this table's owner and must never be explicitly granted
      `UPDATE`/`DELETE` on it) and that the RLS policy on `sensitive_data_access_logs` is still in
      place: migration `20260722163442_EnforceRowLevelSecurityOnSensitiveDataAccessLog`
      (`src/Vlms.Infrastructure/Migrations/`) still enables and forces row-level security with
      `SELECT`/`INSERT` policies and no `UPDATE`/`DELETE` policy.

## V16 Security Logging — manual review items

- [ ] `SensitiveDataAuditInterceptor` still fires on every code path that reads `DbsCheck`/
      `ConsentSensitiveDetails` — in particular, confirm no new query anywhere in the codebase
      projects either entity via `.Select(...)` into an anonymous type *before* materializing the
      entity itself (the exact regression the c0ff6b3 checker round-trip found and fixed in
      `ConsentExpiryJob.SweepDbsAsync` — a projection skips `IMaterializationInterceptor` entirely).
      Grep for `.Select(` near `DbsCheck`/`ConsentSensitiveDetails` and check each hit materializes
      the entity first. Since adr/0006 this covers the Teacher and Parent read paths too:
      `StudentConsentViewService.GetStudentAsync` and `ParentConsentService.GetMyChildrenAsync`
      materialize whole `ConsentSensitiveDetails` entities before mapping them to view records, and
      the audit row carries the Teacher's/Parent's own `UserId`
      (`TeacherRead_WritesOneAuditRowPerDetailsRow_AttributedToTheTeacher`,
      `ParentRead_WritesAuditRow_AttributedToTheParent_AndNoneForHiddenRows`). The former
      `MAX(id)` aggregate over `ConsentSensitiveDetails` in `ConsentRecordService` is gone (a details
      row now takes its record's id), so no aggregate over that table remains.
