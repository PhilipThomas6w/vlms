# RAID Log

Status: in progress (per ISO 31000:2018 — proportionate to a solo-delivered project)

## Risks

- **R-001:** Special-category/children's data (safeguarding, medical, consent, DBS) is managed in-system; a data-protection failure has real safeguarding consequences, not just reputational cost. Mitigation: `governance/security-compliance.md`, OWASP ASVS-aligned NFRs, and — added across three design-review passes — the `ConsentRecord`/`ConsentSensitiveDetails` entity split with structural whole-entity access control (`adr/0004-sensitive-data-access-control.md`: EF Core global query filters + `IMaterializationInterceptor`-based read audit log) and verified guardian-linking (`design/data-design.md`), closing gaps the initial design left open (no read-audit trail; no verification that a self-registering parent was genuinely a child's guardian; a masking mechanism that couldn't actually mask individual columns; an audit-write mechanism that couldn't reliably identify which entity was read).
- **R-002:** Solo developer/maintainer — no delivery redundancy. Bus-factor risk for ongoing operation and support.

## Assumptions

- **A-001:** No external safeguarding governing body/regulator beyond general UK law (confirmed with owner).
- **A-002:** Scale remains "tens of users per role" over the ~2-year horizon; architecture is not being designed for hundreds/thousands of users.
- **A-003:** No data migration from the prior spreadsheets — clean start.

## Issues

- None currently open.

- **D-004 (added when the ADR-0004 §4 tamper-protection DENY was re-targeted to `public`; the PostgreSQL port under `adr/0005-hosting-pivot-self-hosted-vps-postgresql.md` made this dependency *more* load-bearing, not just provider-generic; **structurally closed for ordinary roles at pass 8** — see below):** the production application must connect to the database as a **least-privilege role** — able to `SELECT`/`INSERT` on `sensitive_data_access_logs` but **never explicitly granted** `UPDATE`/`DELETE` on it, and never the table owner or a superuser/`BYPASSRLS` role. **Originally a stronger operational requirement than the SQL Server design carried** — checked against current PostgreSQL documentation, not assumed equivalent (`adr/0004-sensitive-data-access-control.md` §4 pass 6): SQL Server's `DENY ... TO public` overrode *any* grant a principal held, so only the table owner/`sysadmin` could bypass it even if mistakenly granted direct access; PostgreSQL's `REVOKE UPDATE, DELETE ON sensitive_data_access_logs FROM PUBLIC` alone had no such override.

  **Update (pass 8, `adr/0004-sensitive-data-access-control.md` Decision §6):** Row-Level Security (`ALTER TABLE ... ENABLE/FORCE ROW LEVEL SECURITY` plus permissive `SELECT`/`INSERT` policies and deliberately no `UPDATE`/`DELETE` policy) now provides a structural, DENY-equivalent block on `UPDATE`/`DELETE` for every role this deployment creates, including the table owner (`vlms_owner`) — closing the gap the paragraph above describes for **ordinary roles**, not just documenting the operational discipline around it. The residual is now narrower and named precisely: only a genuine PostgreSQL **superuser** session, or a role explicitly granted **`BYPASSRLS`**, still bypasses this — the same class of unavoidable residual the original SQL Server DENY always carried via `sysadmin`/`dbo`, not a newly discovered weakness. Neither `vlms_owner` nor `vlms_app` is created with `SUPERUSER` or `BYPASSRLS` (`deploy/postgres/00-create-roles-and-database.sql` — both explicitly `NOSUPERUSER`, and `BYPASSRLS` defaults off and is never granted), so this residual does not apply to either role as currently provisioned. The least-privilege connection discipline below remains good practice and is still required (RLS does not make an over-privileged connection role safe by itself — it specifically means an over-privileged role granted `UPDATE`/`DELETE` directly can *still* be blocked by RLS, but a role connected as a superuser bypasses everything, RLS included), but "never issue `GRANT UPDATE`/`GRANT DELETE` on this table to the app's role" is no longer the sole backstop the way it was between pass 6 and pass 8. Relatedly, any future retention-purge job for `SensitiveDataAccessLog` (the separate 6-year retention concern) must now run as a genuine superuser or `BYPASSRLS` role specifically — not merely "an elevated role," since an ordinary elevated role with a direct `GRANT DELETE` would still be blocked by RLS. **Owner: Philip. Due: before go-live** (a deployment/operations-readiness check, per `delivery-plan.md` Phase 3) — this update closes the *design* gap; the operational verification step in `deploy/README.md` (a live `UPDATE` as `vlms_app` must fail) still needs to be run against a real deployed server, which has not happened yet (no live PostgreSQL server exists for this project as of this pass). See `adr/0004-sensitive-data-access-control.md` §4/§6, `adr/0005-hosting-pivot-self-hosted-vps-postgresql.md`.
